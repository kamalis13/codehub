Module 10 — HTTP

HTTP DELETE

Remove resources from the server — with optimistic or pessimistic strategies

📌 Definition

http.delete<T>(url, options) sends an HTTP DELETE request to remove the resource at the given URL. DELETE is idempotent — deleting a resource that no longer exists returns 404, but the server state remains the same. The response body is often empty (204 No Content).

🤔 Why is it needed?

  • Removing records, cleaning up data, and handling user-initiated deletions in REST APIs
  • Idempotent nature makes retries safe — no risk of double-delete side effects
  • Angular service encapsulates the delete logic cleanly, keeping components thin

⚙️ Internal Working

    

      http.delete() sends an HTTP DELETE verb to the server with no request body by default.
      The server locates the resource by the URL path, removes it from the data store, and responds with
      204 No Content or 200 OK. Angular's HttpClient returns an Observable that emits once on success and
      errors on non-2xx status codes. Because the operation is idempotent, the client can safely retry
      without risk of double-deletion side effects.
    

  


  

    

      
✅ Advantages

      
    
        
  • Idempotent — safe to retry without double-deletion concerns
    • 
        
  • Clean REST semantics for removing resources
    • 
        
  • Optimistic strategy provides instant UI feedback for a snappy user experience
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Optimistic delete can confuse users if the rollback animation occurs unexpectedly
    • 
        
  • Deleted data is typically unrecoverable — requires careful UX confirmation patterns
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always show a confirmation dialog before destructive DELETE operations
    • 
      
  • Implement soft deletes on the server (isDeleted flag) so data can be recovered if needed
    • 
      
  • Use pessimistic delete when data accuracy is critical; use optimistic for low-risk, fast-feedback UX
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Updating the UI before the API confirms the delete (pessimistic flow) — leading to ghost items if the call fails
    • 
      
  • Not handling the 404 case when retrying a DELETE — treating it as an error instead of a successful removal
