Module 10 — HTTP

HTTP PUT

Replace a resource completely — idempotent full update

📌 Definition

http.put<T>(url, body) sends an HTTP PUT request that replaces the entire resource at the given URL with the provided body. PUT is idempotent: sending the same request multiple times produces the same result as sending it once.

🤔 Why is it needed?

  • Updating complete records where all fields are known and must be persisted together
  • Idempotent nature makes it safe to retry on network failures without side effects
  • Standard REST convention for full resource replacement (PUT /api/resource/:id)

🌐 Real-time Example

    

      A user profile edit form loads the existing profile, binds all fields, and on save sends the
      complete object via PUT — any field not included would be cleared on the server. The example
      also contrasts PUT with PATCH to show when each is appropriate.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's HttpClient serialises the body to JSON and sets Content-Type: application/json
      automatically. The PUT request travels over HTTP carrying the full payload. The server replaces its
      stored representation entirely with the incoming body and returns the updated resource (or 204 No Content).
      Because PUT is idempotent, intermediaries and clients can safely resend it on timeout without risk of
      duplicate side effects.
    

  


  

    

      
✅ Advantages

      
    
        
  • Idempotent — safe to retry without double-update side effects
    • 
        
  • Clear REST semantics — signals a full replacement to server and teammates
    • 
        
  • Consistent server state — no stale fields left from a partial update
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Requires sending all fields even when only one changed — larger payloads over the wire
    • 
        
  • Risk of data loss if client state is stale and overwrites a concurrent update from another user
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always fetch the latest version of the resource before sending a PUT to avoid overwriting concurrent changes
    • 
      
  • Use ETags or version fields for optimistic concurrency control to detect conflicts
    • 
      
  • Validate the full object on the client before sending to catch missing required fields early
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Sending only the changed fields in a PUT request — omitted fields are cleared on the server, causing silent data loss
    • 
      
  • Using PUT when PATCH is more appropriate, causing unnecessarily large payloads for simple single-field updates
