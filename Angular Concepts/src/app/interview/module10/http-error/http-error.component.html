HTTP Error Handling

Handle API failures gracefully — local, global, and retry strategies

📌 Definition

HTTP error handling in Angular uses RxJS's catchError operator to intercept failed Observable streams from HttpClient. Angular provides HttpErrorResponse with status code, message, and error body to help diagnose and handle failures appropriately — whether network errors, client errors (4xx), or server errors (5xx).

🤔 Why is it needed?

  • Real APIs fail — network issues, auth expiry, server errors — and unhandled errors crash the UI
  • Graceful error handling prevents blank screens, data loss, and confused users
  • Interceptors centralise error logic so every request benefits without duplicating code in every service

⚙️ Internal Working

    

      When HttpClient receives a non-2xx response (or a network failure), it emits an error on the
      Observable stream instead of a value. catchError intercepts this error channel,
      receives the HttpErrorResponse, and must return a new Observable — either a fallback
      value, EMPTY (complete silently), or throwError() (re-propagate).
      Interceptors are middleware that wrap next.handle(req), so they see errors from all
      HTTP calls in the application without modifying individual services.
    

  


  

    

      
✅ Advantages

      
    
        
  • Centralised error logic via interceptors — one place to log, alert, or redirect
    • 
        
  • Flexible recovery — return fallback data, redirect, or re-throw depending on error type
    • 
        
  • retry() reduces user impact from transient network blips without any extra UI code
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Global interceptors can swallow errors that specific services need to handle differently
    • 
        
  • retry() without delay can flood the server with rapid repeated requests during an outage
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use status === 0 to detect network errors separately from HTTP errors, and message accordingly
    • 
      
  • Prefer retry with exponential backoff over plain retry(n) for production resilience
    • 
      
  • Combine global and local error handling: interceptor for logging/snackbar, service-level for domain recovery
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Swallowing errors with an empty catchError that returns EMPTY — errors disappear silently and are impossible to debug
    • 
      
  • Using retry() without delay — causes a burst of repeated requests that overwhelm a struggling server
