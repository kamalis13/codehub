Lazy Loading Routes

Splitting the app into smaller bundles for faster initial load

📌 Definition

Lazy loading routes defer loading a route's JavaScript bundle until the user actually navigates to that route. Angular splits the app into separate chunks at build time. The initial bundle contains only what is needed to display the first screen, dramatically reducing startup download size.

🤔 Why is it needed?

  • Reduce initial bundle size for faster first meaningful paint
  • Improve Time to Interactive (TTI) for better Lighthouse scores
  • Load admin/power-user features only when accessed
  • Split large apps into independently deployable chunks
  • Critical for mobile users on slow networks

An app that eagerly loads home and about pages but lazy-loads the entire admin area and a profile component, mixing both lazy loading strategies.

    

  


  

    
⚙️ Internal Working

    
Angular CLI's webpack configuration recognizes dynamic import() calls in loadChildren/loadComponent and creates separate JavaScript chunk files at build time. At runtime, when the Router matches a lazy route for the first time, it makes an HTTP request for the chunk file, evaluates it, registers its routes, and then navigates normally. Subsequent visits to the same lazy route use the cached module — no re-download.

  


  

    

      
✅ Advantages

      
    
        
  • Smaller initial bundle — faster startup
    • 
        
  • Independent chunk caching by the browser
    • 
        
  • Guards (canMatch) can prevent bundle download entirely for unauthorized users
    • 
        
  • Preloading strategies give best of both worlds
    • 
        
  • Scales well for large enterprise apps
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • First navigation to a lazy route has a slight delay (download)
    • 
        
  • Requires discipline to keep feature boundaries clean
    • 
        
  • Shared services between eager and lazy modules need careful scoping
    • 
        
  • Debugging chunk loading errors can be tricky
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Lazy load every feature area that isn't on the landing page
    • 
      
  • Use loadComponent for single-component routes
    • 
      
  • Apply PreloadAllModules or a custom strategy for critical paths
    • 
      
  • Protect lazy routes with canMatch to avoid downloading unauthorized code
    • 
      
  • Analyze bundle sizes regularly with webpack-bundle-analyzer
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Importing lazy components eagerly in AppModule (defeats lazy loading)
    • 
      
  • Forgetting canMatch and using only canActivate (bundle still downloads)
    • 
      
  • Not configuring a preloading strategy (jarring delay on first lazy navigate)
    • 
      
  • Putting shared services inside a lazy module's providers (multiple instances)
    •
