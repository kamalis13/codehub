Module 2 — Components

Component Lifecycle

Eight hooks that let you tap into a component's birth, life, and death

📌 Definition

Angular manages the lifecycle of every component — from creation through change detection cycles to final destruction. Angular exposes 8 lifecycle hooks as interfaces (OnInit, OnDestroy, etc.) that your component class can implement. Angular calls these hook methods at specific moments, giving you precise control over initialization, DOM access, and cleanup.

🤔 Why is it needed?

  • Initialization — Load data, set up subscriptions, and configure state in ngOnInit after inputs are ready.
  • Responding to changes — React to @Input changes with ngOnChanges instead of polling.
  • DOM access — Access @ViewChild references safely in ngAfterViewInit.
  • Cleanup — Unsubscribe from observables and clear timers in ngOnDestroy to prevent memory leaks.
  • Custom change detection — Detect mutations inside arrays or objects via ngDoCheck.

🌐 Real-time Example

    

      A DataDashboardComponent receives a userId as @Input.
      In ngOnInit it loads the user's data and subscribes to a live update stream.
      In ngOnChanges it reloads data when the userId changes.
      In ngOnDestroy it unsubscribes to prevent memory leaks.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's change detection engine drives hook execution. When a component is first created,
      Angular calls hooks in strict order: ngOnChanges → ngOnInit → ngDoCheck → ngAfterContentInit →
      ngAfterContentChecked → ngAfterViewInit → ngAfterViewChecked. On every subsequent change detection
      cycle (triggered by zone.js patching of async APIs), Angular calls ngOnChanges (if inputs changed),
      ngDoCheck, ngAfterContentChecked, and ngAfterViewChecked. When the component is
      removed from the DOM, ngOnDestroy is called once.
    

  


  

    

      
✅ Advantages

      
    
        
  • Precise control over initialization and cleanup at the right moment
    • 
        
  • Prevents memory leaks via ngOnDestroy
    • 
        
  • Enables safe DOM manipulation after the view is ready
    • 
        
  • Reacts to input changes without polling or setTimeout hacks
    • 
        
  • Custom change detection logic via ngDoCheck
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • ngDoCheck and ngAfterViewChecked run very frequently — expensive logic here degrades performance
    • 
        
  • Lifecycle order is non-obvious to beginners, leading to timing bugs
    • 
        
  • Forgetting to implement ngOnDestroy causes memory leaks
    • 
        
  • Angular 16+ takeUntilDestroyed() still requires correct injection context
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use ngOnInit for initialization logic — never the constructor (except DI).
    • 
      
  • Always implement ngOnDestroy to unsubscribe or use takeUntilDestroyed() (Angular 16+).
    • 
      
  • Keep ngDoCheck and ngAfterViewChecked lightweight — they run every CD cycle.
    • 
      
  • Check changes['prop'].firstChange in ngOnChanges to skip initial setup if already done in ngOnInit.
    • 
      
  • Declare interface implementations (implements OnInit) for compile-time safety.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Accessing @ViewChild in ngOnInit — it is undefined until ngAfterViewInit.
    • 
      
  • Making HTTP calls in the constructor instead of ngOnInit.
    • 
      
  • Forgetting to unsubscribe in ngOnDestroy — leads to memory leaks and ghost subscriptions.
    • 
      
  • Putting heavy logic in ngDoCheck — it fires on every change detection run.
    • 
      
  • Mutating data in ngAfterViewChecked — causes "ExpressionChangedAfterItHasBeenCheckedError".
    •
