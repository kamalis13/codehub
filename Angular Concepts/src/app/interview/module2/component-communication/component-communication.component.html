Module 2 — Components

Component Communication

Four essential patterns for sharing data between Angular components

📌 Definition

Angular components are isolated by design, so they need explicit mechanisms to share data and trigger actions across each other. There are four primary patterns: (1) Parent → Child via @Input — property binding passes data down; (2) Child → Parent via @Output + EventEmitter — events travel up; (3) Sibling / Cross-tree via a shared Service — services with RxJS observables broadcast state to any component; and (4) Direct access via @ViewChild / @ContentChild — the parent gets a reference to the child's class instance and calls its public methods.

🤔 Why is it needed?

  • Data flow control — Angular enforces unidirectional data flow (top-down) to keep the app predictable.
  • Decoupling — Components should not know each other's internals; communication contracts keep them loosely coupled.
  • State synchronisation — Multiple components can reflect the same state (e.g., cart count) without duplicating data.
  • Reusability — Generic child components remain reusable because they accept data via @Input rather than hardcoding it.

🌐 Real-time Example

    

      In a shopping cart app: the ProductListComponent (parent) passes each
      product via @Input to ProductCardComponent (child). When the user clicks
      "Add to Cart", ProductCardComponent emits the product via @Output. The parent
      listens and calls CartService.add() — a shared service that broadcasts the updated cart
      to a CartIconComponent living in the header (a sibling).
    

    

  


  

    
⚙️ Internal Working

    

      @Input is implemented via property binding — Angular's template compiler generates code that
      assigns the parent expression's value to the child property on every change detection cycle.
      @Output uses EventEmitter (which extends RxJS Subject) — the parent template creates a
      subscriber that runs the handler expression when the Subject emits.
      Shared services use RxJS BehaviorSubject / Subject that any injected component can push
      values to or subscribe to.
      @ViewChild uses Angular's query engine to locate a matching component instance in the
      view tree after the view is initialized.
    

  


  

    

      
✅ Advantages

      
    
        
  • @Input / @Output are explicit, type-safe, and easy to test
    • 
        
  • Shared services enable global state without a full state management library
    • 
        
  • @ViewChild gives imperative, direct control when declarative patterns fall short
    • 
        
  • Unidirectional data flow makes bugs easy to trace
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Prop drilling — passing data through many layers with @Input becomes verbose
    • 
        
  • Services with Subjects can become hard to debug if many components mutate the same state
    • 
        
  • @ViewChild creates tight coupling between parent and child implementation
    • 
        
  • No built-in immutability — shared service state can be mutated accidentally
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Prefer @Input / @Output for direct parent-child communication — it is explicit and testable.
    • 
      
  • Use shared services only when components are not directly related in the tree.
    • 
      
  • Make service state streams read-only externally (asObservable()) to prevent external mutation.
    • 
      
  • Use @ViewChild sparingly — prefer events and inputs to keep components decoupled.
    • 
      
  • For large apps consider NgRx, Akita, or Angular Signals for predictable global state.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Directly mutating @Input objects inside the child — always emit changes up via @Output.
    • 
      
  • Using EventEmitter in a service — use RxJS Subject / BehaviorSubject instead.
    • 
      
  • Forgetting to unsubscribe from service observables in ngOnDestroy.
    • 
      
  • Using @ViewChild before ngAfterViewInit fires.
    • 
      
  • Over-engineering simple parent-child communication with a shared service when @Input suffices.
