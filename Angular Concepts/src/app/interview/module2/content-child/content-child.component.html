@ContentChild

Accessing elements projected into a component via ng-content

📌 Definition

@ContentChild is a decorator that queries projected content — elements passed into a component's <ng-content> slot by the parent consumer — and injects a reference into the host component class. Unlike @ViewChild which queries the component's own template, @ContentChild queries content that lives in the parent's template but is rendered inside this component's slot.

🤔 Why is it needed?

  • Inspect projected content — The host component can read or configure projected child components/elements programmatically.
  • Flexible container components — A card or accordion can enforce constraints (e.g., only one header) by reading projected content.
  • Coordinate between host and projected content — A tab group reads all projected TabPanelComponents to build its navigation bar.

🌐 Real-time Example

    

      A reusable CardComponent has two <ng-content> slots — one for
      the header and one for the body. It uses @ContentChild(CardHeaderComponent) to access
      the projected header and read its title property in ngAfterContentInit.
      This lets the card component log or act on the consumer-supplied header without forcing the consumer
      to pass the title as a separate @Input.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's content query system processes projected content before the host component's own
      view is initialized. The ngAfterContentInit hook fires after all projected content is
      initialized and @ContentChild/@ContentChildren references are resolved.
      The projected content belongs to the parent's change detector, not the host's —
      which means the host cannot directly trigger change detection on projected elements.
      @ContentChildren (plural) returns a live QueryList that emits on its
      changes observable as projected items are dynamically added or removed.
    

  


  

    

      
✅ Advantages

      
    
        
  • Enables powerful, flexible container components (cards, modals, tabs)
    • 
        
  • Projected content keeps the consumer's template clean and declarative
    • 
        
  • Host can inspect and coordinate projected components without tight coupling
    • 
        
  • Works with both components and template reference variables
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Accessing before ngAfterContentInit yields undefined
    • 
        
  • Projected content belongs to parent's change detection — host can't force an update
    • 
        
  • Creates implicit coupling between the host and the projected component's API
    • 
        
  • Harder to discover than @Input — consumers must know what to project
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Access @ContentChild only in ngAfterContentInit or later.
    • 
      
  • Use @ContentChildren for scenarios with multiple projected items (tabs, list items).
    • 
      
  • Document which content types the component expects to receive via projection.
    • 
      
  • Use null-safe access (this.header?.title) since projection is always optional.
    • 
      
  • Prefer CSS attribute selectors in ng-content select="..." over component selectors for greater flexibility.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Confusing @ContentChild with @ViewChild — projected vs own-template content.
    • 
      
  • Accessing the content child in ngOnInit — it is not yet available.
    • 
      
  • Trying to trigger change detection on projected content from the host component — projected content is owned by the parent.
    • 
      
  • Not handling the case where no content is projected — always null-check the result.
    •
