@Input Decorator

One-way data binding — passing data from parent to child component

📌 Definition

@Input() is a decorator that marks a class property as an input binding, allowing a parent component to pass data into a child component via property binding syntax ([propertyName]="expression"). Data flows one way: from parent down to child. The child receives the value but should not mutate it directly — changes should flow back up via @Output.

🤔 Why is it needed?

  • Configurability — The same component can render different data depending on what the parent passes in.
  • Reusability — A ProductCardComponent becomes generic when it accepts any product object as input.
  • Unidirectional data flow — Parent owns the data; child only reads it, keeping state changes traceable.
  • OnPush compatibility — When inputs are immutable objects, OnPush change detection works optimally.

🌐 Real-time Example

    

      A ProductCardComponent receives a Product object from a parent product list.
      It uses @Input({ required: true }) (Angular 16+) to enforce that the parent always
      provides a product. It implements ngOnChanges to log when the product changes — useful
      when the user navigates between different products.
    

    

  


  

    
⚙️ Internal Working

    

      During compilation, Angular's template compiler generates a property setter for each @Input
      binding. When the parent's expression value changes, Angular's change detection engine calls that setter,
      which assigns the new value to the child's property and schedules an update. With
      ChangeDetectionStrategy.OnPush, Angular only triggers change detection on the child
      when an @Input reference changes (shallow equality check), not when nested
      properties mutate. ngOnChanges fires after each input update with a SimpleChanges
      map detailing previous and current values.
    

  


  

    

      
✅ Advantages

      
    
        
  • Explicit, readable, and type-safe data passing
    • 
        
  • Makes components configurable and reusable
    • 
        
  • Works seamlessly with OnPush for performance
    • 
        
  • @Input({ required: true }) (Angular 16+) enforces contracts at compile time
    • 
        
  • Aliases keep the public API stable while internals change
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Prop drilling through many layers is verbose and tedious
    • 
        
  • Only detects reference changes by default — deep mutations require ngOnChanges or DoCheck
    • 
        
  • Requires discipline to avoid mutating the input object inside the child
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use @Input({ required: true }) for inputs that must always be provided (Angular 16+).
    • 
      
  • Use an alias when the external API name should differ from the internal property name.
    • 
      
  • Validate input values in a setter: set value(v) { this._value = v < 0 ? 0 : v; }.
    • 
      
  • Never mutate the input object — treat it as read-only and emit changes upward via @Output.
    • 
      
  • Pass immutable (spread or new object) values to child inputs to leverage OnPush efficiently.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Mutating the @Input object directly — breaks unidirectional data flow.
    • 
      
  • Forgetting to declare the @Input decorator — the property is silently ignored in the template.
    • 
      
  • Accessing the input value in the constructor — it is not set until ngOnInit at the earliest.
    • 
      
  • Using @Input when a shared service would be more appropriate for deeply nested or sibling components.
