@Output Decorator

Emitting custom events from child to parent — the child-to-parent data channel

📌 Definition

@Output() is a decorator that exposes an EventEmitter on a child component, enabling the child to send data or notifications to its parent via event binding ((eventName)="handler($event)"). A child should never modify parent state directly — it should emit an event with the relevant payload, and the parent decides what to do with it.

🤔 Why is it needed?

  • Unidirectional flow — Children communicate upward through events, keeping data flow predictable.
  • Decoupling — The child does not need a reference to the parent; it simply emits an event.
  • Reusability — A generic SignupFormComponent is reusable because it emits events rather than knowing which service to call.
  • Two-way binding — Pairing @Input() value with @Output() valueChange enables the [(value)] banana-in-a-box syntax.

🌐 Real-time Example

    

      A SignupFormComponent renders a registration form. When the user submits, it emits
      a registered event containing the user's name and email. When the user cancels, it emits
      a void cancelled event. The parent decides whether to navigate away, call an API, or
      show a success message — the form component remains generic and reusable.
    

    

  


  

    
⚙️ Internal Working

    

      EventEmitter extends RxJS Subject. When Angular's template compiler processes
      (registered)="onRegistered($event)", it creates a subscription to the child's
      registered EventEmitter. Calling emit(payload) calls Subject.next(payload),
      which synchronously invokes the subscriber (the parent's handler). Angular automatically unsubscribes
      when the child component is destroyed, preventing memory leaks for parent-bound outputs.
    

  


  

    

      
✅ Advantages

      
    
        
  • Keeps data flow unidirectional and easy to debug
    • 
        
  • Type-safe with EventEmitter<T>
    • 
        
  • Components remain decoupled and reusable
    • 
        
  • Enables the two-way binding shorthand [(value)]
    • 
        
  • Parent automatically unsubscribes when child is destroyed
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Only the direct parent can listen — not suitable for cross-tree communication
    • 
        
  • Events must bubble through every intermediate parent in deeply nested trees
    • 
        
  • EventEmitter should not be used in services — use RxJS Subject instead
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always type your EventEmitter: new EventEmitter<User>() — avoid any.
    • 
      
  • Use past-tense or noun-based names for outputs: userSelected, formSubmitted.
    • 
      
  • Use the valueChange naming convention to enable [(value)] two-way binding.
    • 
      
  • Keep the emitted payload minimal — only what the parent needs to act.
    • 
      
  • Do not use EventEmitter in services; use RxJS Subject there instead.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using EventEmitter in a service for cross-component communication (use Subject).
    • 
      
  • Emitting complex, mutable objects — the parent may inadvertently share the same reference.
    • 
      
  • Not typing the EventEmitter — the parent's handler receives an untyped $event.
    • 
      
  • Calling .subscribe() directly on a child's @Output EventEmitter from parent TypeScript code.
    • 
      
  • Forgetting the Change suffix in the output name when implementing custom two-way binding.
    •
