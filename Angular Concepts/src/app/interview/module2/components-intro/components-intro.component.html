Module 2 — Components

Angular Components

The fundamental building blocks that compose every Angular UI

📌 Definition

An Angular component is a TypeScript class decorated with @Component that controls a reusable section of the user interface. Every Angular application is a tree of components starting from a single root. Each component combines a template (HTML), styles (CSS), and a class (TypeScript) that defines the data and behaviour behind that view.

🤔 Why is it needed?

  • UI Composition — Break a complex page into small, focused pieces that are easier to build and test.
  • Reusability — A single component (e.g., UserCardComponent) can be used anywhere in the app with different data.
  • Encapsulation — Each component owns its template and styles, preventing accidental side-effects on other parts of the UI.
  • Separation of concerns — Business logic lives in the class, presentation in the template, and appearance in the styles.
  • Testability — Isolated components are simple to unit-test with Angular's TestBed or standalone testing utilities.

🌐 Real-time Example

    

      A UserCardComponent receives a user object via @Input and renders an avatar, name,
      email, and role badge. It is reused inside a user list, a search result page, and a profile sidebar — the
      same component with different data each time.
    

    

  


  

    
⚙️ Internal Working

    

      When Angular bootstraps, it reads the root component's selector and replaces the matching host
      element in index.html. Angular constructs a component tree: each component's
      template may contain child component selectors, which Angular instantiates recursively. A
      change detector is created for every component. During each change detection cycle (triggered
      by events, HTTP responses, or timers via zone.js), Angular checks each component's bindings and updates the
      DOM only where values have changed.
    

  


  

    

      
✅ Advantages

      
    
        
  • Clear separation of concerns via template, class, and styles
    • 
        
  • Strong reusability — one definition, used many times
    • 
        
  • Scoped styles prevent global CSS conflicts
    • 
        
  • Standalone components reduce NgModule boilerplate
    • 
        
  • Easy to test in isolation with Angular's testing utilities
    • 
        
  • Excellent tooling (Angular CLI, DevTools, Storybook)
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Overhead for very simple use-cases that a directive would suffice
    • 
        
  • Learning curve for change detection and lifecycle hooks
    • 
        
  • Deeply nested trees can cause performance issues without OnPush
    • 
        
  • Over-componentizing leads to unnecessary complexity
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Follow the Single Responsibility Principle — one component, one purpose.
    • 
      
  • Use ChangeDetectionStrategy.OnPush for pure/presentational components.
    • 
      
  • Prefer standalone components to avoid NgModule overhead in new code.
    • 
      
  • Keep templates thin — move complex logic into the class or a service.
    • 
      
  • Name components clearly: UserCardComponent, not Card1Component.
    • 
      
  • Use Angular CLI (ng generate component) to ensure consistent file structure.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Putting HTTP calls or business logic directly in the component class (use services instead).
    • 
      
  • Not importing CommonModule / required modules in standalone components, causing *ngIf or *ngFor to silently fail.
    • 
      
  • Using ViewEncapsulation.None unintentionally, causing CSS to bleed globally.
    • 
      
  • Forgetting to declare the selector prefix (e.g., app-) leading to HTML spec warnings.
    • 
      
  • Creating massive "god components" that handle dozens of responsibilities.
    •
