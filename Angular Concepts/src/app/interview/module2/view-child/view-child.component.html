Module 2 — Components

@ViewChild

Programmatic access to child components and DOM elements from the parent class

📌 Definition

@ViewChild is a property decorator that queries the component's own template for a matching child component, directive, or DOM element and injects a reference into the parent class. You can query by component/directive class, template reference variable (#name), or a provider token. @ViewChildren (plural) retrieves all matches as a live QueryList<T>.

🤔 Why is it needed?

  • Imperative child control — Call child methods directly (e.g., form.reset(), chart.refresh()).
  • DOM access — Get a reference to a native DOM element via ElementRef for focus management or measurements.
  • Third-party library integration — Initialise a chart, map, or D3 visualization that needs a real DOM element.
  • Template refs — Access TemplateRef instances for dynamic rendering via ngTemplateOutlet.

🌐 Real-time Example

    

      A WizardComponent contains a StepFormComponent. The wizard needs
      to check if the form is valid before advancing to the next step and reset the form when the user
      clicks "Reset". Using @ViewChild, the wizard gets a direct reference to the form
      component and calls its isValid() and resetForm() methods from
      ngAfterViewInit onward.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's view query system runs after the component's view (template) is compiled and rendered.
      With static: false (default), the query is resolved after the first change
      detection run, which is why ngAfterViewInit is the earliest safe hook.
      With static: true, the query is resolved at compile time before change detection,
      making the reference available in ngOnInit — but only if the element is not
      conditionally rendered. @ViewChildren returns a live QueryList that
      emits on its changes observable whenever items are added or removed.
    

  


  

    

      
✅ Advantages

      
    
        
  • Enables imperative control when declarative @Input/@Output is insufficient
    • 
        
  • Direct DOM access for integrating third-party libraries
    • 
        
  • Strongly typed reference to child component's public API
    • 
        
  • @ViewChildren provides a live list that auto-updates
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Creates tight coupling between parent and child implementation details
    • 
        
  • Direct nativeElement access breaks server-side rendering (Angular Universal)
    • 
        
  • Accessing before ngAfterViewInit yields undefined
    • 
        
  • Makes refactoring the child harder — parent may depend on its internal structure
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Prefer @Input/@Output for standard data flow — use @ViewChild only when imperative access is truly needed.
    • 
      
  • Access @ViewChild only inside ngAfterViewInit or later hooks.
    • 
      
  • Use Renderer2 instead of nativeElement to keep code SSR-safe.
    • 
      
  • Use the ?. optional chaining operator when accessing @ViewChild that may be conditionally rendered.
    • 
      
  • Document why @ViewChild is used — it signals a non-standard communication pattern.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Accessing @ViewChild in ngOnInit — it is undefined until ngAfterViewInit.
    • 
      
  • Using static: true on a conditionally rendered element (*ngIf) — will always be undefined.
    • 
      
  • Mutating the child's internal state directly instead of calling its public API methods.
    • 
      
  • Directly manipulating nativeElement for styling — use [class] or [style] bindings instead.
    •
