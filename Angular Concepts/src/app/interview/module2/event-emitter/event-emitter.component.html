Module 2 — Components

EventEmitter

Angular's mechanism for emitting custom events — powered by RxJS Subject

📌 Definition

EventEmitter<T> is an Angular class that extends RxJS Subject. It adds an emit(value) method (which internally calls Subject.next(value)) to make it feel natural in Angular's component model. It is almost always used together with the @Output decorator to create custom component events that the parent template can bind to with (eventName)="handler($event)".

🤔 Why is it needed?

  • Custom DOM-like events — Allows components to emit semantic events (e.g., productSelected) just like the DOM emits click or input events.
  • Child-to-parent communication — The only official mechanism for a child to send data up to its parent in a type-safe way.
  • Decoupling — The child does not know who listens; it simply emits, making the component reusable.
  • RxJS integration — Since it extends Subject, advanced patterns (pipe, take, filter) are possible, though rarely needed for @Output bindings.

🌐 Real-time Example

    

      A CustomButtonComponent keeps an internal click counter. Each time the button
      is clicked, it increments the counter and emits the new count via a typed
      EventEmitter<number>. The parent receives each emission and displays the
      running total in its own template — demonstrating typed event payloads and child-to-parent
      data flow.
    

    

  


  

    
⚙️ Internal Working

    

      Because EventEmitter extends Subject, calling emit(value) calls
      Subject.next(value). The parent's (event)="handler($event)" binding creates
      a subscription. By default, emission is synchronous — the handler runs in the same
      call stack as emit(). Passing true to the constructor —
      new EventEmitter(true) — wraps emission in setTimeout(fn, 0), making it
      asynchronous. Angular's template binding system automatically unsubscribes when the child component
      is destroyed, preventing memory leaks.
    

  


  

    

      
✅ Advantages

      
    
        
  • Familiar API: emit() mirrors native DOM dispatchEvent()
    • 
        
  • Type-safe with generics: EventEmitter<User>
    • 
        
  • Extends Subject — all RxJS operators are available when needed
    • 
        
  • Parent subscription is automatically managed by Angular
    • 
        
  • Async option defers events to avoid change detection issues
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Not suitable for cross-component communication in services — use Subject there
    • 
        
  • Only one-hop: child → direct parent (no event bubbling through the component tree)
    • 
        
  • Calling .subscribe() manually on a child's @Output is an anti-pattern
    • 
        
  • Synchronous by default — can trigger change detection at unexpected times if misused
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always type the EventEmitter: new EventEmitter<Product>().
    • 
      
  • Use EventEmitter only with @Output in components — use Subject in services.
    • 
      
  • Name outputs semantically: itemDeleted, filterChanged, not click2.
    • 
      
  • Emit copies of objects (spread) rather than original references to avoid accidental shared mutation.
    • 
      
  • Don't subscribe manually to a sibling's @Output — use a shared service instead.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using EventEmitter inside a service for inter-component messaging (use Subject).
    • 
      
  • Calling subscribe() on a child's @Output from parent TypeScript — Angular won't manage lifecycle.
    • 
      
  • Forgetting to include @Output() decorator — the EventEmitter becomes just a regular property, not a bindable event.
    • 
      
  • Using EventEmitter<any> — loses type safety in parent handler.
    •
