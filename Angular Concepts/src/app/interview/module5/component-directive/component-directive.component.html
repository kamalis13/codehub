Module 5 — Directives

Component Directive

The most powerful directive — a directive with its own template and view

📌 Definition

A Component Directive is a directive with a template. It is declared with the @Component decorator, which internally extends @Directive. Every Angular component is technically a directive — @Component adds template, styles, and view-encapsulation on top of the base directive API. Components are the building blocks of Angular UIs.

🤔 Why is it needed?

  • Encapsulates HTML, CSS, and TypeScript logic into a single reusable unit
  • Enables component composition — complex UIs built from small, testable pieces
  • Provides a clear contract through @Input() and @Output() APIs
  • Supports view encapsulation so styles don't bleed into other components
  • Foundation for lazy loading, routing, and change detection tree

⚙️ Internal Working

    
Angular's compiler processes the @Component decorator metadata to generate a component factory. At runtime, the Angular runtime matches the selector in the DOM, creates a component instance, attaches it to the change detection tree, and renders the template. Lifecycle hooks (ngOnInit, ngOnChanges, etc.) fire at defined phases. The component's view is linked to the component class so data binding updates the DOM automatically during change detection.

  


  

    

      
✅ Advantages

      
    
        
  • Fully encapsulates UI logic, template, and styles in one unit
    • 
        
  • Promotes reusability across the application
    • 
        
  • Independently testable with TestBed
    • 
        
  • Works with Angular's change detection and DI system seamlessly
    • 
        
  • Supports OnPush for high-performance rendering
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Heavier than plain attribute directives — creates its own view
    • 
        
  • Overhead of full component lifecycle when only behavior modification is needed
    • 
        
  • Can lead to over-componentisation (splitting too much) impacting readability
    • 
        
  • Each component adds to the bundle (mitigated by lazy loading)
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Follow the Single Responsibility Principle — one component, one concern
    • 
      
  • Use standalone: true and avoid NgModule boilerplate where possible
    • 
      
  • Use ChangeDetectionStrategy.OnPush for leaf/presentational components
    • 
      
  • Keep smart (container) and dumb (presentational) components clearly separated
    • 
      
  • Always use templateUrl and styleUrl for non-trivial components
    • 
      
  • Name selectors with a consistent app prefix (e.g., app-) to avoid conflicts
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Putting too much business logic directly in a component instead of a service
    • 
      
  • Forgetting to add a new component to the parent's imports array (standalone) or declarations (NgModule)
    • 
      
  • Using Default change detection everywhere instead of OnPush where appropriate
    • 
      
  • Mutating @Input values directly inside the child component
    • 
      
  • Skipping trackBy in lists rendered by this component, causing performance issues
    •
