Module 5 — Directives

Custom Directive

Build reusable behavior that can be applied to any element — the power of @Directive

📌 Definition

A Custom Directive is a user-defined Angular directive created with the @Directive decorator. It encapsulates reusable behavior (tooltip, copy-to-clipboard, drag-and-drop, auto-focus, etc.) that can be applied to any DOM element as an attribute. Custom directives use @HostListener for event handling, @HostBinding for host property binding, and @Input() for configuration.

🤔 Why is it needed?

  • Encapsulate DOM-manipulation behavior that applies to many elements across the app
  • DRY principle — define tooltip, validation highlight, or copy-to-clipboard once, use everywhere
  • Keeps behavior logic in TypeScript where it is unit-testable
  • Works with Angular's DI, lifecycle hooks, and change detection
  • Clean separation — host component doesn't need to know how the behavior works

⚙️ Internal Working

    
Angular processes all @Directive classes imported (standalone) or declared (NgModule) in scope. When the directive's selector matches a host element, Angular creates a directive instance, injecting all DI tokens. @HostBinding properties are evaluated during change detection and applied to the host element via Renderer2. @HostListener registers native DOM event listeners on the host element. Lifecycle hooks (ngOnInit, ngOnDestroy) fire at the usual times.

  


  

    

      
✅ Advantages

      
    
        
  • Highly reusable — apply to any element type anywhere in the app
    • 
        
  • Lightweight — no template overhead like a component
    • 
        
  • Full access to DI — inject services, Router, HttpClient, etc.
    • 
        
  • Supports full Angular lifecycle (ngOnInit, ngOnDestroy, ngOnChanges)
    • 
        
  • Configurable via @Input() for maximum flexibility
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Cannot render its own template or HTML
    • 
        
  • Complex directives are harder to test than components (need a host element)
    • 
        
  • Overuse can make templates harder to read ("what does this attribute do?")
    • 
        
  • Direct ElementRef usage breaks SSR — must use Renderer2 for compatibility
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always prefix selector with app (or your team prefix) to avoid conflicts
    • 
      
  • Prefer @HostBinding over ElementRef.nativeElement for property binding
    • 
      
  • Use Renderer2 for programmatic DOM manipulation (SSR-safe)
    • 
      
  • Clean up subscriptions and DOM listeners in ngOnDestroy
    • 
      
  • Make directives single-purpose — one behavior per directive
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using ElementRef.nativeElement directly — breaks SSR and bypasses security
    • 
      
  • Forgetting to export the directive from its module or add to standalone imports
    • 
      
  • Not calling ngOnDestroy to unsubscribe or remove DOM listeners
    • 
      
  • Naming selector without a prefix — can conflict with native HTML attributes
    • 
      
  • Putting too much logic in @HostListener — extract to private methods for readability
    •
