Module 5 — Directives

ngStyle

Set inline styles dynamically — bind CSS properties directly to component state

📌 Definition

[ngStyle] is a built-in attribute directive that sets one or more inline styles on a DOM element using an object expression. Keys are CSS property names (camelCase or kebab-case in quotes) and values are the style values including units. It is used when style values are truly dynamic (e.g., user-chosen colors, calculated widths, progress percentages) and cannot be predetermined in a CSS class.

🤔 Why is it needed?

  • Set styles whose values are dynamic — not known at compile time (e.g., percentage widths)
  • Apply user-customizable themes (colors, font sizes selected by the user)
  • Animate component-input dimensions (progress bars, charts, draggable elements)
  • Compute style objects from component state without cluttering the template
  • No need for direct ElementRef.nativeElement.style manipulation

⚙️ Internal Working

    
The NgStyle directive subscribes to the bound object expression. During change detection, it compares the new style object to the previous one using a KeyValueDiffer. For each changed property, it calls Renderer2.setStyle(element, prop, value). For removed properties, it calls Renderer2.removeStyle(). Using Renderer2 instead of direct DOM access ensures SSR compatibility and security.

  


  

    

      
✅ Advantages

      
    
        
  • Cleanly binds multiple dynamic styles from a single expression
    • 
        
  • Works with both camelCase and kebab-case CSS property names
    • 
        
  • Uses Renderer2 internally — SSR-compatible and secure
    • 
        
  • Supports CSS transitions for animated style changes
    • 
        
  • Merges with existing inline styles; does not replace them all
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Inline styles have high specificity — hard to override with classes
    • 
        
  • Not ideal for static/predictable styles (use CSS classes instead)
    • 
        
  • Object literal in template triggers unnecessary diff checks each cycle
    • 
        
  • Reduces separation of concerns — styling logic mixes into TypeScript
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Compute the style object in a getter, not as an inline object literal in the template
    • 
      
  • Use [style.property.unit] (e.g., [style.width.%]) for single-property bindings
    • 
      
  • Prefer CSS classes and [ngClass] over [ngStyle] for predictable values
    • 
      
  • Reserve [ngStyle] for truly dynamic values: user-input colors, calculated dimensions
    • 
      
  • Include transition in the style object to get smooth CSS animations for free
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using [ngStyle] instead of a CSS class for styles that don't change at runtime
    • 
      
  • Forgetting to include units in values: 'font-size': '14' instead of '14px'
    • 
      
  • Passing an inline object literal — creates new reference every change detection cycle
    • 
      
  • Using [ngStyle] when [style.width.%] is cleaner for a single property
    • 
      
  • Forgetting to import NgStyle or CommonModule in standalone components
    •
