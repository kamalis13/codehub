Module 12 — Lifecycle Hooks

ngAfterContentChecked

Called after every change detection pass on projected content — use with caution due to high frequency

📌 Definition

ngAfterContentChecked is an Angular lifecycle hook that fires after every change detection cycle that checks the component's projected content. It is the recurring counterpart to ngAfterContentInit (which fires only once). After the first cycle it fires in the sequence: ngDoCheck → ngAfterContentChecked. Because it fires on every CD cycle, it must contain only very lightweight, fast operations to avoid performance degradation.

🤔 Why is it needed?

  • Allows reacting to repeated state changes in projected content after each CD pass
  • Enables recalculating summary/derived state from projected children
  • Provides a hook for monitoring projected content health (e.g., counting errors)
  • Complements ngAfterContentInit — init sets up, checked maintains
  • Used by Angular's form infrastructure to track validation state across projected fields

🌐 Real-time Example

    
A FormGroupComponent wraps projected FormFieldComponent children. After each change detection pass, ngAfterContentChecked counts how many projected fields have errors and updates a summary message. This gives a live "N fields have errors" counter that updates as the user fills in the form.

    

  


  

    
⚙️ Internal Working

    
Angular's change detection processes the component tree from root to leaves. For each component, the sequence on every CD cycle (after first initialization) is: ngDoCheck → ngAfterContentChecked → ngAfterViewChecked. Angular calls ngAfterContentChecked() after it has finished checking all @ContentChildren for changes. In development mode, Angular runs a second verification pass — which is why modifying bound properties in this hook without calling detectChanges() throws ExpressionChangedAfterItHasBeenCheckedError.

  


  

    

      
✅ Advantages

      
    
        
  • Provides a hook into every projected-content check — maximum reactivity
    • 
        
  • Can recalculate derived values from @ContentChildren state on each cycle
    • 
        
  • Consistent, predictable firing after every CD pass
    • 
        
  • Works with ChangeDetectorRef.detectChanges() to safely update state mid-cycle
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Fires extremely frequently — can cause severe performance issues if misused
    • 
        
  • Modifying bound properties here causes ExpressionChangedAfterItHasBeenCheckedError in dev mode
    • 
        
  • Heavy logic in this hook makes the entire application sluggish
    • 
        
  • Often a symptom of poor architecture — consider QueryList.changes or signals instead
    • 
        
  • Difficult to debug performance issues originating here
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Keep logic extremely lightweight — O(1) operations only
    • 
      
  • Use caching/flags to avoid redundant calculations on every cycle
    • 
      
  • Prefer QueryList.changes subscription (set up in ngAfterContentInit) for less frequent updates
    • 
      
  • Use ChangeDetectorRef.detectChanges() if you must modify bound state in this hook
    • 
      
  • Consider Angular signals (Angular 16+) as a modern, push-based alternative
    • 
      
  • Implement implements AfterContentChecked for TypeScript enforcement
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Placing expensive logic (loops, API calls) in ngAfterContentChecked
    • 
      
  • Modifying template-bound properties without calling detectChanges() — causes ExpressionChangedError
    • 
      
  • Using ngAfterContentChecked when ngAfterContentInit + QueryList.changes would suffice
    • 
      
  • Not realizing it fires on every event in the app, not just content-specific events
    • 
      
  • Confusing it with ngAfterViewChecked (view vs. content distinction)
    •
