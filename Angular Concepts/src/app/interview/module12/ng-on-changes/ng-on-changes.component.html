Module 12 — Lifecycle Hooks

ngOnChanges

Called every time an @Input() property changes — the reactive bridge between parent and child

📌 Definition

ngOnChanges is an Angular lifecycle hook that fires whenever one or more @Input()-decorated properties of a component receive a new value from the parent. It is called before ngOnInit on the first cycle, then again every subsequent time an input binding changes. It receives a SimpleChanges object providing details on what changed, with previous and current values available for comparison.

🤔 Why is it needed?

  • Allows a child component to react dynamically when parent data changes
  • Provides access to both the old and new input values for comparison logic
  • Enables conditional API calls only when a specific input changes
  • Guards against running expensive logic on the very first binding (isFirstChange())
  • Works before the view renders, so you can compute derived state before the DOM updates

🌐 Real-time Example

    
In a product catalogue, a parent passes productId to a ProductDetailComponent. When the user selects a different product, the parent updates selectedId, which flows down as an @Input(). The child uses ngOnChanges to fetch new product data whenever productId changes without destroying and re-creating the component.

    

  


  

    
⚙️ Internal Working

    
During every change detection cycle, Angular compares the current and previous values of each @Input() binding using strict reference equality (===). If any input has changed, Angular calls ngOnChanges(changes) on the component, passing a SimpleChanges object only containing the properties that changed. This happens synchronously before the view is updated. For objects and arrays, Angular checks the reference, not deep equality — so mutating an object in-place will NOT trigger ngOnChanges.

  


  

    

      
✅ Advantages

      
    
        
  • Provides previousValue and currentValue for smart diffing
    • 
        
  • Works with every @Input() in the component — single hook handles all inputs
    • 
        
  • isFirstChange() cleanly separates initial load from subsequent updates
    • 
        
  • Fires before the DOM updates — ideal for computing derived state
    • 
        
  • No need to destroy/re-create a component when parent data changes
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Does NOT detect mutations inside objects or arrays (shallow comparison only)
    • 
        
  • Can cause performance issues if expensive logic runs on every input change
    • 
        
  • Requires implementing OnChanges interface — adds boilerplate
    • 
        
  • Not triggered if the input binding is missing from the parent template
    • 
        
  • Can become complex when many inputs change independently
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always check which specific input changed using if (changes['inputName'])
    • 
      
  • Guard initial load logic with isFirstChange() to avoid duplicate API calls with ngOnInit
    • 
      
  • Use immutable data patterns (spread/Object.assign) to ensure object changes trigger ngOnChanges
    • 
      
  • Implement implements OnChanges so TypeScript enforces the correct method signature
    • 
      
  • For complex diffing logic, consider ngDoCheck with KeyValueDiffer instead
    • 
      
  • Keep ngOnChanges lightweight — delegate heavy work to services or computed properties
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Expecting ngOnChanges to fire when object properties mutate (it checks reference only)
    • 
      
  • Forgetting to check isFirstChange() and duplicating the ngOnInit HTTP call
    • 
      
  • Using ngOnChanges on non-@Input() properties — it only monitors @Input() bindings
    • 
      
  • Not guarding against null or undefined currentValue in early cycles
    • 
      
  • Placing ngOnChanges logic without implements OnChanges — TypeScript won't warn of typos
    •
