Module 12 — Lifecycle Hooks

ngAfterViewInit

Called once after the component's view is fully rendered — the only safe place to access @ViewChild and initialize DOM-dependent libraries

📌 Definition

ngAfterViewInit is an Angular lifecycle hook that fires once after Angular has fully created, rendered, and initialized the component's own view and all its child component views. At this point, @ViewChild and @ViewChildren queries are resolved, all template reference variables (e.g., #myInput) are bound to real DOM elements or component instances, and child components have completed their own initialization lifecycle.

🤔 Why is it needed?

  • @ViewChild is undefined until this hook — it is the only safe access point
  • DOM elements are rendered and available — required for third-party libraries (Chart.js, D3, Mapbox)
  • Child component instances are fully initialized — safe to call their methods
  • Allows auto-focusing inputs, measuring element dimensions, and initializing canvas/WebGL contexts
  • Provides a clear, guaranteed "view ready" signal from Angular's lifecycle system

🌐 Real-time Example

    
A location picker component needs to auto-focus a search input and initialize a Mapbox GL map inside a div. Both operations require actual DOM elements — impossible before the view renders. In ngAfterViewInit(), both @ViewChild references are available. The map instance is stored for cleanup in ngOnDestroy().

    

  


  

    
⚙️ Internal Working

    
Angular's lifecycle order: Constructor → ngOnChanges → ngOnInit → ngDoCheck → ngAfterContentInit → ngAfterContentChecked → ngAfterViewInit → ngAfterViewChecked. Angular processes all child component views recursively before calling the parent's ngAfterViewInit. So by the time ngAfterViewInit fires in the parent, all child components have fully initialized their own views. Angular resolves @ViewChild/@ViewChildren queries by scanning the component's template DOM subtree for matching selectors, types, or template reference variables.

  


  

    

      
✅ Advantages

      
    
        
  • Guaranteed DOM availability — @ViewChild always resolves here
    • 
        
  • All child component instances fully initialized — safe to call child methods
    • 
        
  • Fires only once — no risk of re-initializing libraries on every CD cycle
    • 
        
  • Works with @ViewChildren and QueryList.changes for dynamic view children
    • 
        
  • Standard pattern recognized by all Angular developers for third-party lib initialization
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Modifying parent-bound properties here causes ExpressionChangedAfterItHasBeenCheckedError
    • 
        
  • Fires only once — dynamic view child changes require QueryList.changes subscription
    • 
        
  • Direct DOM manipulation (nativeElement) bypasses Angular's abstraction — breaks SSR
    • 
        
  • Heavy initialization here can delay the first visible render to the user
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always initialize DOM-dependent third-party libraries in ngAfterViewInit, never earlier
    • 
      
  • Store library instances in component properties for cleanup in ngOnDestroy
    • 
      
  • Use ChangeDetectorRef.detectChanges() when you must update bound properties in this hook
    • 
      
  • Add if (isPlatformBrowser(this.platformId)) guard for SSR compatibility
    • 
      
  • Subscribe to @ViewChildren.changes in ngAfterViewInit for dynamic child tracking
    • 
      
  • Implement implements AfterViewInit for TypeScript type checking
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Accessing @ViewChild in ngOnInit — always returns undefined (most common mistake)
    • 
      
  • Forgetting to clean up third-party library instances in ngOnDestroy (memory leaks)
    • 
      
  • Modifying parent-bound properties in ngAfterViewInit without detectChanges()
    • 
      
  • Using nativeElement access without an SSR platform guard
    • 
      
  • Calling child component methods in ngOnInit instead of ngAfterViewInit
    •
