Module 12 — Lifecycle Hooks

ngOnInit

Called once after first ngOnChanges — the canonical place for HTTP calls and initialization logic

📌 Definition

ngOnInit is an Angular lifecycle hook that is called exactly once, after Angular has initialized all @Input() property bindings and run the first change detection pass. It is the recommended entry point for all component initialization logic — HTTP requests, Observable subscriptions, route parameter reading, and derived-state computation. It runs after ngOnChanges (if inputs exist) and never runs again for the same component instance.

🤔 Why is it needed?

  • @Input() values are fully resolved here — safe to use in API calls
  • Separates initialization logic from dependency injection (constructor stays clean)
  • Angular Universal (SSR) depends on ngOnInit as the initialization boundary
  • TestBed controls when ngOnInit runs — making unit tests predictable
  • Route parameters via ActivatedRoute are available here

🌐 Real-time Example

    
An analytics dashboard component receives a dateRange as an @Input() from the parent. In ngOnInit(), it subscribes to route params (with takeUntil for cleanup) and triggers an API call using both the route param and the fully-resolved @Input() value — something impossible to do correctly in the constructor.

    

  


  

    
⚙️ Internal Working

    
After the constructor runs and DI completes, Angular's component factory calls ngOnChanges() (if the component has any @Input() bindings with initial values), then immediately calls ngOnInit(). This happens synchronously during the first ApplicationRef.tick() (change detection cycle). Angular calls ngOnInit() via a lifecycle hook check — it looks for a method named ngOnInit on the component instance. Implementing OnInit interface is optional but recommended as it makes TypeScript enforce the correct signature and helps IDEs with autocomplete.

  


  

    

      
✅ Advantages

      
    
        
  • All @Input() bindings are resolved — safe for API calls with input-based parameters
    • 
        
  • Runs only once — no risk of duplicate initialization on re-renders
    • 
        
  • TestBed controls execution — tests can set up mocks before fixture.detectChanges()
    • 
        
  • Consistent pattern across the Angular ecosystem — every Angular developer knows ngOnInit
    • 
        
  • Works seamlessly with Angular Universal SSR
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Does not re-run when @Input() values change — use ngOnChanges for that
    • 
        
  • async ngOnInit errors can be swallowed if not explicitly caught
    • 
        
  • Cannot be called manually — only Angular's runtime invokes it
    • 
        
  • If logic depends on both ngOnInit and ngOnChanges, ordering must be carefully managed
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always implement implements OnInit — TypeScript will catch method name typos
    • 
      
  • Place all HTTP calls, subscriptions, and initialization logic here
    • 
      
  • Pair with ngOnDestroy to unsubscribe from Observables set up in ngOnInit
    • 
      
  • Use takeUntil(this.destroy$) pattern for automatic subscription cleanup
    • 
      
  • Keep ngOnInit readable — delegate complex logic to private helper methods or services
    • 
      
  • For input-reactive logic (re-runs on input change), move it to ngOnChanges instead
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Placing HTTP calls in constructor instead of ngOnInit (most common mistake)
    • 
      
  • Expecting ngOnInit to fire again when @Input() changes — it will not
    • 
      
  • Forgetting fixture.detectChanges() in unit tests — ngOnInit won't be called
    • 
      
  • Using async ngOnInit without try/catch — unhandled promise rejections are silent
    • 
      
  • Duplicating logic between ngOnInit and ngOnChanges, causing double API calls
    •
