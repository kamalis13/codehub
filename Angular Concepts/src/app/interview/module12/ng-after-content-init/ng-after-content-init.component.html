Module 12 — Lifecycle Hooks

ngAfterContentInit

Called once after ng-content projection is complete — the safe entry point for @ContentChild queries

📌 Definition

ngAfterContentInit is an Angular lifecycle hook that fires once after Angular has projected external content (via <ng-content>) into the component's view and fully initialized the projected child components. At this point, @ContentChild and @ContentChildren queries are resolved and available. It is the counterpart to ngAfterViewInit — but for projected content rather than the component's own template elements.

🤔 Why is it needed?

  • @ContentChild and @ContentChildren are only available after this hook
  • Enables initialization logic on projected child components (e.g., activate the first tab)
  • Allows subscribing to QueryList.changes for dynamic content updates
  • Provides a clear, safe boundary — no guessing about when projected content is ready
  • Used in reusable container components: tabs, accordions, carousels, modals

🌐 Real-time Example

    
An AccordionComponent uses <ng-content> to accept AccordionPanelComponent children. In ngAfterContentInit(), it queries all projected panels via @ContentChildren, subscribes to each panel's toggle event, and subscribes to panels.changes to handle dynamically added panels. This is a pattern used in Angular Material's MatTabGroup.

    

  


  

    
⚙️ Internal Working

    
Angular's lifecycle order for a component with content projection: Constructor → ngOnChanges → ngOnInit → ngDoCheck → ngAfterContentInit → ngAfterContentChecked → ngAfterViewInit → ngAfterViewChecked. The projected content goes through its own initialization cycle before the parent's ngAfterContentInit fires. Angular resolves @ContentChild/@ContentChildren queries after this phase by scanning the projected DOM subtree for matching selectors, component types, or template reference variables.

  


  

    

      
✅ Advantages

      
    
        
  • Guaranteed safe access to @ContentChild and @ContentChildren
    • 
        
  • Fires only once — ideal for one-time setup on projected content
    • 
        
  • Works with QueryList.changes for dynamic/lazy projected content
    • 
        
  • Enables powerful composition patterns — wrapper components with projected slots
    • 
        
  • Clean separation from view initialization (ngAfterViewInit handles own view)
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Only fires once — dynamic changes to projected content need QueryList.changes subscription
    • 
        
  • Accessing @ContentChild in earlier hooks (ngOnInit) is a common mistake (returns undefined)
    • 
        
  • Tight coupling between container and projected child component types
    • 
        
  • Modifying component state in ngAfterContentChecked (not ngAfterContentInit) can cause ExpressionChangedAfterItHasBeenCheckedError
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always access @ContentChild/@ContentChildren in ngAfterContentInit, never earlier
    • 
      
  • Subscribe to QueryList.changes for dynamic content and unsubscribe in ngOnDestroy
    • 
      
  • Implement implements AfterContentInit for TypeScript type safety
    • 
      
  • Keep content initialization logic in ngAfterContentInit, not ngAfterContentChecked (performance)
    • 
      
  • Use @ContentChildren(ComponentClass) rather than string selectors for type safety
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Accessing @ContentChild in ngOnInit — always returns undefined
    • 
      
  • Confusing @ContentChild (projected content) with @ViewChild (own template)
    • 
      
  • Not subscribing to QueryList.changes when projected items can be added dynamically
    • 
      
  • Modifying bound properties in ngAfterContentChecked, triggering ExpressionChangedAfterItHasBeenCheckedError
    • 
      
  • Forgetting to unsubscribe from QueryList.changes in ngOnDestroy
    •
