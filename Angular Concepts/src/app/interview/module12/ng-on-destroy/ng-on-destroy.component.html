Module 12 — Lifecycle Hooks

ngOnDestroy

Called just before the component is destroyed — the essential cleanup hook to prevent memory leaks in SPAs

📌 Definition

ngOnDestroy is an Angular lifecycle hook called immediately before Angular destroys a component instance and removes it from the DOM. It is the final lifecycle hook — Angular calls it when a component is removed via *ngIf going false, during route navigation away from the component, or when a list item is removed from *ngFor. It is the canonical place for all cleanup: unsubscribing Observables, clearing timers, releasing DOM event listeners, and destroying third-party library instances.

🤔 Why is it needed?

  • Unsubscribed Observables continue executing even after the component is gone — causing memory leaks
  • Active setInterval timers keep running and may try to update a destroyed component
  • Third-party library instances (Chart.js, Mapbox) hold references to DOM nodes
  • In SPAs, components are created/destroyed on every route change — leaks accumulate over time
  • Angular's garbage collector cannot clean up active subscriptions — you must do it explicitly

🌐 Real-time Example

    
A dashboard component subscribes to a WebSocket for live notifications, sets up a 30-second auto-refresh interval, and subscribes to a notification service EventEmitter. All three require cleanup when the user navigates away. The takeUntil(destroy$) pattern handles all Observable subscriptions with a single destroy$.next(), while clearInterval handles the timer.

    

  


  

    
⚙️ Internal Working

    
When Angular destroys a component, it: (1) calls ngOnDestroy() synchronously; (2) detaches the component's view from the view tree; (3) destroys all child components recursively (each gets its own ngOnDestroy call); (4) removes the component's DOM nodes; (5) releases the component's injector. Angular's Router triggers this chain on every navigation. If a component has child components, ngOnDestroy is called depth-first — children are destroyed before parents.

  


  

    

      
✅ Advantages

      
    
        
  • Guaranteed single cleanup point — all resource management in one method
    • 
        
  • takeUntil pattern cleans up ALL subscriptions with one line
    • 
        
  • Called before DOM removal — can still access DOM if needed for teardown
    • 
        
  • Angular 16+ DestroyRef enables cleanup without implementing OnDestroy interface
    • 
        
  • async pipe auto-calls ngOnDestroy unsubscription — no manual work for template subscriptions
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Not called when the browser tab/window is forcefully closed
    • 
        
  • Easy to forget — a single missing unsubscribe causes a subtle memory leak
    • 
        
  • takeUntil Subject must be both nexted AND completed — forgetting complete() leaks the Subject itself
    • 
        
  • Cannot perform async operations in ngOnDestroy (HTTP calls, Promises) — they won't complete
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use takeUntil(this.destroy$) for all Observable subscriptions in ngOnInit
    • 
      
  • Always call both destroy$.next() AND destroy$.complete() in ngOnDestroy
    • 
      
  • Use Angular 16+ takeUntilDestroyed() from @angular/core/rxjs-interop as the modern alternative
    • 
      
  • Always clean up: timers (clearInterval/clearTimeout), listeners (removeEventListener), library instances
    • 
      
  • Use the async pipe in templates instead of manual subscriptions where possible
    • 
      
  • Implement implements OnDestroy — TypeScript will warn if ngOnDestroy is misspelled
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Not unsubscribing from long-lived Observables (WebSocket, polling intervals)
    • 
      
  • Calling only destroy$.next() without destroy$.complete() — leaks the Subject
    • 
      
  • Forgetting to clearInterval — the timer keeps running and may throw errors on a destroyed component
    • 
      
  • Not cleaning up third-party library instances — causes DOM reference leaks
    • 
      
  • Trying to make HTTP calls in ngOnDestroy — the component is gone before the call returns
    •
