Module 4 — Templates

Template Reference Variable

Grab a direct reference to any DOM element, directive, or component right in the template

📌 Definition

A Template Reference Variable is a local label declared in the HTML template using the #variableName syntax. It captures a reference to the element, directive, or component it is attached to, making that reference available anywhere in the same template without touching the TypeScript class. On a plain element, it holds the HTMLElement. On a directive, it holds the directive instance (via #ref="directiveName"). On a component, it holds the component instance, exposing its public methods and properties directly in the template.

🤔 Why is it needed?

  • Access element without ViewChild — read inputRef.value or focus an element in the template itself.
  • Pass to methods — pass #inputRef to a component method to operate on the element.
  • NgForm access — capture the NgForm directive with #form="ngForm" to read validation state.
  • Component method calls — call child component methods directly in the template (#player.play()).
  • ng-template handles — reference templates for use with *ngTemplateOutlet.

🌐 Real-time Example

    

      A ContactFormComponent uses #contactForm="ngForm" to access the form's
      validation state and call form.resetForm() after submission. A #nameInput
      reference is passed to a focusField() method that programmatically focuses and selects
      the input text — all without a single ViewChild or DOM query in the TypeScript class.
    

    

  


  

    
⚙️ Internal Working

    

      At compile time, Angular's template compiler identifies all #varName declarations and
      assigns each a unique slot in the view's local variables array (the template context). When
      the view is created, Angular populates each slot with the appropriate reference — the native element,
      directive export, or component instance. Template expressions that reference these variables are
      compiled into direct slot lookups, making access O(1). The scope is limited to the enclosing view
      node, which is why variables inside *ngIf or *ngFor are not reachable
      from the outer template.
    

  


  

    

      
✅ Advantages

      
    
        
  • Zero TypeScript code needed for simple template-only interactions (focus, value read, method call).
    • 
        
  • Provides access to NgForm validation state cleanly via #form="ngForm".
    • 
        
  • Can call child component public methods directly from the parent template.
    • 
        
  • Works with ng-template for advanced template projection and outlet patterns.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Only available inside the template — cannot use the variable in the TypeScript class (use @ViewChild instead).
    • 
        
  • Scoped to the current view — not accessible outside structural directives like *ngIf or *ngFor.
    • 
        
  • Over-reliance on template variables for complex logic leads to untestable, hard-to-read templates.
    • 
        
  • Calling component methods directly from the template tightly couples the parent template to child internals.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use template variables for simple, template-only concerns (focus, value read, reset); use @ViewChild for class-level access.
    • 
      
  • Always export directive instances explicitly: #form="ngForm" rather than relying on the default element reference.
    • 
      
  • Avoid placing a #ref inside *ngIf/*ngFor blocks if you need to access it outside that block.
    • 
      
  • Prefer template variables over manually querying the DOM via document.getElementById or ElementRef.nativeElement.
    • 
      
  • Use ng-template with #tplRef to create reusable template fragments for *ngTemplateOutlet.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Declaring #ref inside an *ngIf block and trying to use it outside — Angular cannot resolve it; it is undefined in the outer scope.
    • 
      
  • Forgetting ="ngForm" — #form without the export targets the HTMLFormElement, not the NgForm directive.
    • 
      
  • Accessing a template variable from the TypeScript class — variables only exist in the template; use @ViewChild instead.
    • 
      
  • Using template variables for complex logic — move computation to the component class for testability.
    • 
      
  • Having two elements with the same #name in the same template scope — the second declaration shadows the first, causing confusion.
    •
