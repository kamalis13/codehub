Two-way Binding

Synchronise component data and template inputs simultaneously — the "banana in a box" pattern

📌 Definition

Two-way Binding combines property binding and event binding into a single, concise syntax — [(ngModel)]="property". The square brackets push the component property's value into the DOM element (view ← component), and the parentheses listen for user changes and push the new value back to the component property (view → component). This bidirectional sync is also called the "banana in a box" syntax because the parentheses (banana) sit inside the square brackets (box).

🤔 Why is it needed?

  • Form inputs — keeps component state and input value in sync without separate property + event bindings.
  • Live preview — changes typed by the user are reflected instantly in other parts of the template.
  • Reduced boilerplate — replaces a separate [value] binding and (input) event handler with one line.
  • Template-driven forms — ngModel is the foundation of Angular's template-driven form approach.
  • Custom components — implement two-way binding for child components using @Input + @Output xChange convention.

🌐 Real-time Example

    

      A SearchBarComponent uses [(ngModel)]="searchQuery" so that typing in the
      input immediately updates searchQuery, which is reflected in the "Searching for:" paragraph
      below it. The Clear button resets searchQuery = '' and the input field clears simultaneously
      because of two-way binding — no manual DOM manipulation needed.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's NgModel directive implements the ControlValueAccessor interface.
      The [ngModel] part calls writeValue() on the accessor to set the DOM element's
      value from the component. The (ngModelChange) part listens to the element's native
      input event (or change for checkboxes/selects), extracts the new value,
      and calls onChange(), which emits it through the ngModelChange EventEmitter.
      Angular's change detection then assigns the emitted value back to the component property.
    

  


  

    

      
✅ Advantages

      
    
        
  • Concise — one binding replaces a separate [value] + (input) pair.
    • 
        
  • Instant sync — changes in the input are immediately available in the component and vice versa.
    • 
        
  • Works with all standard form elements: text, number, checkbox, radio, select, textarea.
    • 
        
  • Custom components can implement it using the @Input + @Output xChange pattern.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Requires FormsModule import — easy to forget in lazy-loaded or standalone modules.
    • 
        
  • Bidirectional data flow makes debugging harder — a value change could originate from either side.
    • 
        
  • Not suitable for complex forms — use Reactive Forms (FormGroup, FormControl) for validation, async validators, and dynamic fields.
    • 
        
  • Template-driven forms have limited testability compared to Reactive Forms.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use [(ngModel)] for simple, standalone form inputs; prefer Reactive Forms for complex forms.
    • 
      
  • Always import FormsModule in the module or standalone component where ngModel is used.
    • 
      
  • Use (ngModelChange)="handler($event)" when you need to react to changes with side effects (e.g., API calls).
    • 
      
  • Name @Output as propertyNameChange when implementing two-way binding on custom components.
    • 
      
  • Avoid two-way binding in child components of OnPush parents — use explicit input/output pairs for predictable change detection.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Forgetting to import FormsModule — Angular throws "Can't bind to 'ngModel'" compilation error.
    • 
      
  • Using [(ngModel)] on a form element inside a <form> without a name attribute — required when using ngForm.
    • 
      
  • Mutating the bound object directly instead of reassigning — can cause change detection issues with OnPush components.
    • 
      
  • Using two-way binding for complex forms instead of Reactive Forms — leads to untestable, hard-to-validate forms.
    • 
      
  • Misnaming the @Output on a custom component (e.g., valueUpdated instead of valueChange) — breaks the [(value)] two-way binding convention.
    •
