Property Binding

One-way data flow from component to DOM — set any element property dynamically

📌 Definition

Property Binding is a one-way Angular data-binding mechanism that evaluates a TypeScript expression and assigns its result to a DOM property (or a child component's @Input). Written as [property]="expression", Angular wraps the target in square brackets to distinguish it from a plain HTML attribute. Data flows in one direction — from component to view — and Angular keeps the property in sync on every change detection cycle.

🤔 Why is it needed?

  • Dynamic DOM properties — set src, href, disabled, and other properties from component data.
  • Type safety — unlike interpolation (always a string), property binding passes the actual type — boolean, number, or object.
  • Component communication — primary mechanism to pass data down to child components via @Input.
  • Reactive UI — the DOM updates automatically when the bound expression's value changes.
  • Accessibility — dynamically set aria-* attributes via [attr.aria-label].

🌐 Real-time Example

    

      A ProductFormComponent dynamically sets the product image src, disables
      the Submit button while submitting or when the form is invalid, applies a CSS class based on stock level,
      and controls the button's loading state — all driven by component properties without a single DOM query.
    

    

  


  

    
⚙️ Internal Working

    

      At AOT compilation time, Angular resolves [property]="expr" into a DOM property assignment
      in the generated view factory. At runtime, during change detection, Angular evaluates the expression in
      the component's scope. If the value differs from the previous tick (dirty check), Angular calls
      renderer.setProperty(element, 'property', newValue) on the target DOM element. This is
      more efficient than full DOM diffing because Angular knows exactly which property to update. For
      attribute binding ([attr.x]), Angular calls renderer.setAttribute() instead.
    

  


  

    

      
✅ Advantages

      
    
        
  • Passes correct types (boolean, number, object) — no string coercion issues.
    • 
        
  • Covers all DOM properties including those without HTML attribute equivalents.
    • 
        
  • Works for child component @Input — the backbone of component communication.
    • 
        
  • Supports class, style, and attribute sub-bindings for rich UI control.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • One-way only — use two-way binding or event binding to propagate changes back to the component.
    • 
        
  • Cannot bind to HTML attributes that don't map to DOM properties (use [attr.x] instead).
    • 
        
  • Slight learning curve around the attributes-vs-properties distinction for newcomers.
    • 
        
  • Heavy computed expressions run on every change detection cycle — use memoised getters.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Prefer property binding over interpolation whenever the target needs a non-string value.
    • 
      
  • Use [class.name]="bool" for single-class toggles and [ngClass] for multiple.
    • 
      
  • Use [style.prop.unit]="number" for numeric CSS values (px, %, em) to avoid string concatenation.
    • 
      
  • Use [attr.x] for ARIA attributes, table attributes (colspan), and SVG properties.
    • 
      
  • Define complex expressions as component getters — easier to test and memoised by the browser.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using disabled="{{ isDisabled }}" — the string "false" still disables the element; always use [disabled]="isDisabled".
    • 
      
  • Confusing [value] (DOM property, current value) with value="..." (HTML attribute, initial value).
    • 
      
  • Using [innerHTML] with unsanitised user input — opens XSS vulnerabilities; use Angular's DomSanitizer.
    • 
      
  • Binding to non-existent DOM properties — Angular silently ignores unknown properties in non-strict mode; enable strictTemplates in tsconfig to catch these.
    • 
      
  • Using [attr.colspan] where [colSpan] (camelCase DOM property) would work — both are valid, but be consistent.
    •
