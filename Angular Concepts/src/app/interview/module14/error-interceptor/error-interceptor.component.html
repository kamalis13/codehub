Module 14 — Interceptors

Error Interceptor

Centralized HTTP error handling — catch 401/403/500 errors once, show global notifications, and redirect as needed

📌 Definition

An Error Interceptor is an Angular HTTP interceptor that uses the RxJS catchError operator to intercept HttpErrorResponse objects from failed HTTP requests. Instead of writing error handling logic in every service method and component, the error interceptor centralizes it — detecting specific HTTP error codes (401, 403, 404, 500), taking appropriate action (redirect, toast, retry, logging), and then re-throwing the error for any local handling that components need to do.

🤔 Why is it needed?

  • DRY — HTTP error handling logic in one place instead of every service
  • 401 → automatic logout and redirect to /login across all API calls
  • 403 → redirect to /access-denied without repeating logic in each component
  • 500 → show a global toast notification automatically
  • Logging — send every HTTP error to an observability service (Datadog, Sentry)
  • Retry — automatically retry transient server errors (5xx) with backoff

🌐 Real-time Example

    
A production error interceptor combines: smart retry (only for 5xx, not 4xx), structured logging to a monitoring service, 401 handling with token refresh attempt before forcing logout, 403 redirect to /access-denied, 5xx toast notification, and always re-throwing so components can handle local error states (disable submit button, show inline error).

    

  


  

    
⚙️ Internal Working

    
The error interceptor wraps next(req) with a pipe(catchError(...)). When any HTTP call in the Angular app returns a non-2xx status, Angular's HttpBackend creates an HttpErrorResponse and propagates it as an Observable error through the interceptor chain. catchError intercepts this error Observable and can either handle it (return a new Observable), recover from it (return EMPTY or a default value), or re-throw with throwError(() => error). The chain processes from innermost to outermost interceptor on errors — opposite to the outgoing request direction.

  


  

    

      
✅ Advantages

      
    
        
  • Single place for all HTTP error logic — reduces code duplication significantly
    • 
        
  • Automatic 401 → logout redirect without touching any service or component
    • 
        
  • Retry logic for transient failures without changing individual services
    • 
        
  • Easy to add new error types or change handling without touching service code
    • 
        
  • Works with logging services for production observability (Sentry, Datadog)
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Can hide errors from components if re-throw is forgotten (always re-throw!)
    • 
        
  • Complex when combined with token refresh — risk of infinite 401 loops
    • 
        
  • Generic error handling may not suit every component's specific needs
    • 
        
  • Over-centralization — some errors are better handled locally with specific UX
    • 
        
  • Race conditions with refresh token BehaviorSubject queue need careful implementation
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always re-throw with throwError(() => error) — never swallow errors silently
    • 
      
  • Guard against infinite loops: skip refresh logic when the request IS the refresh endpoint
    • 
      
  • Use retry() before catchError() for transient 5xx errors; never retry 4xx
    • 
      
  • Inject a logging service and log all errors for production observability
    • 
      
  • Register the error interceptor LAST in the chain so it catches all errors from other interceptors
    • 
      
  • Handle status 0 separately — indicates a network error (no internet, CORS, server offline)
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Not re-throwing the error — components never know the request failed
    • 
      
  • Retrying 4xx errors — these are client-side issues that retrying cannot fix
    • 
      
  • Creating an infinite refresh loop — refresh endpoint itself returns 401, triggering another refresh
    • 
      
  • Showing generic "Unknown error" toast for 401/403 — specific messages improve UX
    • 
      
  • Logging out the user on a 403 — they are authenticated, just not authorized for this resource
