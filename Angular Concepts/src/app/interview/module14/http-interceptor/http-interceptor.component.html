Module 14 — Interceptors

HTTP Interceptor

Middleware for the Angular HTTP pipeline — intercept, transform, and handle every request and response in one place

📌 Definition

An Angular HTTP Interceptor is a middleware mechanism that sits between the Angular HttpClient and the actual HTTP backend. It intercepts every outgoing request and incoming response, allowing you to inspect and transform them without modifying individual service methods. Interceptors solve cross-cutting concerns — logic that applies to many/all HTTP calls (authentication, logging, error handling, caching, spinners) is written once and applied automatically.

🤔 Why is it needed?

  • Centralized auth token injection — add Bearer header once, applies to all API calls
  • Global error handling — catch 401/403/500 errors in one place
  • Request/response logging — trace every API call without touching services
  • Loading spinners — show on request start, hide on response/error
  • Response caching — return cached data for identical GET requests
  • Request retrying — automatically retry failed requests with exponential backoff

🌐 Real-time Example

    
A request timing interceptor clones the request to add a X-Request-Id header and X-Client-Version, measures the round-trip time, and logs it with the request ID. Multiple interceptors chain together — timing first, then auth token, then error handling — each running in registration order for outgoing requests and in reverse for responses.

    

  


  

    
⚙️ Internal Working

    
Angular's HttpClient builds a chain of interceptors using a linked-list structure. When you call httpClient.get(url), Angular creates an HttpRequest and passes it to the first interceptor. Each interceptor calls next(req) (functional) or next.handle(req) (class-based) to pass the request to the next interceptor in the chain. The last "interceptor" is the HttpBackend, which actually performs the XMLHttpRequest/fetch. The response Observable flows back through the chain in reverse, passing through each interceptor's pipe() operators.

  


  

    

      
✅ Advantages

      
    
        
  • DRY principle — auth, logging, error handling written once, applied everywhere
    • 
        
  • Composable chain — multiple interceptors are stacked in a predictable order
    • 
        
  • Request immutability via req.clone() prevents accidental corruption
    • 
        
  • Observable-based — full RxJS power (retry, catchError, switchMap) available
    • 
        
  • Functional interceptors (Angular 15+) are simpler and tree-shakable
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • All interceptors run for ALL HttpClient calls — need URL guards for selective application
    • 
        
  • Complex interceptor chains are hard to debug (no visual middleware diagram)
    • 
        
  • Order-sensitive — wrong registration order can cause subtle bugs
    • 
        
  • Class-based interceptors require HTTP_INTERCEPTORS multi-token boilerplate
    • 
        
  • Interceptors cannot easily skip themselves without explicit URL or context checks
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use functional interceptors (Angular 15+) for new projects — simpler, tree-shakable
    • 
      
  • Use HttpContext tokens (not URL checks) to conditionally skip interceptors
    • 
      
  • Keep each interceptor focused on a single concern (SRP)
    • 
      
  • Always clone the request before modifying it — never mutate req directly
    • 
      
  • Handle errors in interceptors with catchError and re-throw with throwError()
    • 
      
  • Register interceptors in a dedicated file or app.config.ts for clarity
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Forgetting to call next(req) — the request never reaches the server
    • 
      
  • Mutating req directly instead of using req.clone()
    • 
      
  • Not handling errors in the interceptor — unhandled errors break the entire app
    • 
      
  • Calling HTTP endpoints inside an interceptor without guards — infinite loops
    • 
      
  • Registering duplicate interceptors — same logic runs twice per request
    •
