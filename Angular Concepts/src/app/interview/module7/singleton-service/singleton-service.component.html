Module 7 — Services

Singleton Service

One instance shared across the entire application

📌 Definition

A singleton service is a service of which Angular creates exactly one instance, shared across the entire application. Any component or service that injects it gets the same object reference. This makes singletons ideal for shared state, caching, and cross-component communication.

🤔 Why is it needed?

  • Share authenticated user state across the entire app
  • Cache HTTP responses once, reuse everywhere
  • Enable cross-component communication without @Input/@Output chains
  • Coordinate application-wide operations (auth, analytics, feature flags)
  • Reduce memory by reusing one object instead of many

🌐 Real-time Example

    
An AuthService holds the currently logged-in user. The header component, dashboard, and settings all inject the same AuthService instance and see the same user. Logging out in one place is instantly reflected everywhere.

    

  


  

    
⚙️ Internal Working

    
When providedIn: 'root' is used, Angular's tree-shaking-aware compiler registers the service with the root injector during app bootstrap. The first injection triggers instantiation; subsequent injections return the cached instance from the root injector's registry. The instance lives for the entire application lifetime.

  


  

    

      
✅ Advantages

      
    
        
  • One authoritative source of truth for shared data
    • 
        
  • Memory efficient — single instance throughout app life
    • 
        
  • State changes are instantly visible to all consumers
    • 
        
  • Easy cross-component communication via Observables
    • 
        
  • Built-in with Angular — no extra libraries needed
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Global mutable state is hard to reason about
    • 
        
  • Singleton state persists across navigation (can be stale)
    • 
        
  • Testing requires resetting shared state between test cases
    • 
        
  • Hard to isolate in component-level unit tests
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use BehaviorSubject/Signal for reactive shared state
    • 
      
  • Keep singleton services focused on one concern
    • 
      
  • Provide a reset() method for testing and logout flows
    • 
      
  • Avoid storing UI state in services — keep it in components
    • 
      
  • Use Angular DevTools to inspect service instances
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Re-providing a root service in a component or module (creates duplicate)
    • 
      
  • Storing component-specific state in a singleton (state pollution)
    • 
      
  • Not resetting singleton state on user logout
    • 
      
  • Mutating arrays in place instead of creating new references (change detection misses it)
    •
