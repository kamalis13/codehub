Module 7 — Services

Injector

The container that holds and creates service instances

📌 Definition

An Injector is Angular's internal container (registry + factory) that stores provider configurations and creates service instances on demand. Every Angular application has a tree of injectors mirroring the component tree. When a dependency is requested, Angular's injector resolves it by walking up the tree.

🤔 Why is it needed?

  • Manages the lifecycle of all injectable objects
  • Implements the singleton pattern at the appropriate scope
  • Enables hierarchical scoping — different components can get different service instances
  • Provides lazy instantiation — services are created only when first requested
  • Makes testing possible by swapping implementations at the injector level

🌐 Real-time Example

    
A child component uses @SkipSelf() to get the parent's LogService instance instead of its own, and @Optional() for an analytics service that may not be configured in all environments.

    

  


  

    
⚙️ Internal Working

    
Angular builds an injector tree parallel to the component tree. Each injector has a parent reference. When resolving a token, Angular starts at the component's ElementInjector, checks its registry, then walks up via parent references through ModuleInjector to the RootInjector and finally NullInjector. @Self and @SkipSelf modify this walk. The resolved instance is cached so subsequent lookups return the same object.

  


  

    

      
✅ Advantages

      
    
        
  • Hierarchical scoping gives fine-grained control over service lifetime
    • 
        
  • Lazy instantiation — services created only when needed
    • 
        
  • Testing is easy — swap providers in TestBed at any injector level
    • 
        
  • @Optional prevents hard crashes for optional integrations
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Deep hierarchies make injection debugging complex
    • 
        
  • Component-level providers can create unexpected multiple instances
    • 
        
  • @SkipSelf misuse causes hard-to-find bugs
    • 
        
  • Understanding the full hierarchy requires experience
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Reserve component-level providers for truly scoped services
    • 
      
  • Use @Optional for services that may not always be configured
    • 
      
  • Avoid injecting Injector directly — prefer explicit dependencies
    • 
      
  • Document component-level providers with a comment explaining why
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Providing the same service at multiple levels unintentionally (duplicate instances)
    • 
      
  • Using @Self when @SkipSelf was intended
    • 
      
  • Forgetting @Optional on optional services (crash if not provided)
    • 
      
  • Injecting Injector as a workaround instead of restructuring dependencies
    •
