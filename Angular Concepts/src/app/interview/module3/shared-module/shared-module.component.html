Module 3 — Modules

Shared Module

Centralise reusable components, pipes, and directives — import once, use everywhere

📌 Definition

A Shared Module is an NgModule that declares and exports reusable building blocks — UI components (buttons, spinners, modals), custom pipes (currency format, truncate), and directives (highlight, tooltip) — that multiple feature modules need. Any feature module can import SharedModule to gain instant access to all these shared pieces without duplicating declarations, following the DRY (Don't Repeat Yourself) principle.

🤔 Why is it needed?

  • Avoid duplicate imports — a component can only be declared in one module; SharedModule is the correct single declaration point.
  • DRY principle — write once, export, and reuse across all feature modules.
  • Consistency — ensures every feature uses the same Button, Spinner, and Pipe implementations.
  • Less boilerplate — feature modules import one SharedModule instead of listing five separate imports.
  • Easier maintenance — updating a shared component propagates the change to all consumers automatically.

⚙️ Internal Working

    

      When Angular compiles a feature module that imports SharedModule, it merges the exports of
      SharedModule into the feature module's compilation scope. This means templates in
      ProductListComponent can reference <app-button> or
      currencyFormat pipe as if they were declared locally. Under AOT compilation, Angular resolves
      all template references at build time, so unused exports from SharedModule are still bundled
      unless you migrate to standalone components, which support true per-component tree-shaking.
    

  


  

    

      
✅ Advantages

      
    
        
  • Eliminates the "declared in multiple modules" error by centralising declarations.
    • 
        
  • Single source of truth for shared UI — one change propagates everywhere.
    • 
        
  • Simplifies feature module imports: one import gives access to many components.
    • 
        
  • Re-exporting CommonModule gives feature modules ngIf and ngFor for free.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Do NOT provide services here — each import creates a fresh instance, breaking singletons.
    • 
        
  • SharedModule can become bloated over time, bundling components a module never uses.
    • 
        
  • Not compatible with optimal tree-shaking — standalone components handle this better.
    • 
        
  • Must be explicitly imported in every lazy-loaded module; inheritance does not apply.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Only export what multiple modules actually use — keep SharedModule lean.
    • 
      
  • Never register services or provide tokens in SharedModule; use providedIn: 'root' instead.
    • 
      
  • Re-export CommonModule for convenience, but avoid re-exporting heavy modules unnecessarily.
    • 
      
  • Consider splitting into sub-shared modules (UiSharedModule, FormSharedModule) as the app grows.
    • 
      
  • Migrate shared pieces to standalone components in Angular 14+ projects for better tree-shaking.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Providing services in SharedModule — creates multiple service instances, one per importing module.
    • 
      
  • Exporting everything — causes large bundle size; only export what consumers need.
    • 
      
  • Not exporting CommonModule — feature module templates fail to find ngIf / ngFor.
    • 
      
  • Importing SharedModule in CoreModule, which itself is imported in AppModule — unnecessary duplication.
    • 
      
  • Declaring the same component in both SharedModule and a feature module — Angular compilation error.
    •
