Module 3 — Modules

Feature Module

Group related functionality into cohesive, independently loadable modules

📌 Definition

A Feature Module is an NgModule that encapsulates all Angular building blocks (components, directives, pipes, services, and routing) for a specific domain or feature of the application — such as Products, Orders, or Authentication. Feature modules are imported into AppModule eagerly or registered as lazy-loaded routes, keeping each slice of functionality self-contained and independently maintainable.

🤔 Why is it needed?

  • Code organisation — keeps domain code together instead of scattering it across a monolithic AppModule.
  • Lazy loading — Angular can split feature modules into separate JS bundles loaded on demand.
  • Separation of concerns — teams can own individual feature modules without merge conflicts.
  • Independent testing — feature modules can be compiled and tested in isolation.
  • Reusability — a feature module can be included in multiple projects with minimal changes.

🌐 Real-time Example

    

      In an e-commerce app, the ProductsModule owns ProductListComponent,
      ProductDetailComponent, ProductsRoutingModule, and ProductService.
      The router lazy-loads this module only when the user navigates to /products, keeping the
      initial bundle small and improving time-to-interactive.
    

    

  


  

    
⚙️ Internal Working

    

      When Angular's router encounters a lazy route, it uses Webpack's dynamic import() to fetch
      the feature module's chunk from the server. Angular's module loader then compiles (or reads the AOT factory of)
      that chunk, creates a child NgModuleRef with its own injector (child of the root injector),
      and renders the routed component. Services provided directly in the feature module are scoped to this child
      injector — each lazy load creates a fresh instance unless the service uses providedIn: 'root'.
    

  


  

    

      
✅ Advantages

      
    
        
  • Enables lazy loading, dramatically reducing initial bundle size.
    • 
        
  • Enforces domain-driven design and clear architectural boundaries.
    • 
        
  • Allows parallel development by separate teams without conflicts.
    • 
        
  • Makes unit and integration testing more focused and faster.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • More files and boilerplate compared to a single-module or standalone approach.
    • 
        
  • Circular dependencies between modules can cause hard-to-debug build errors.
    • 
        
  • Lazy-loaded modules need FormsModule / ReactiveFormsModule imported explicitly — easy to forget.
    • 
        
  • Service scoping in lazy modules can surprise developers expecting singletons.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always create a dedicated routing module (XyzRoutingModule) inside each feature module.
    • 
      
  • Use RouterModule.forChild(routes) — never forRoot() — in feature routing.
    • 
      
  • Import only what the feature needs; avoid importing SharedModule if only one component is needed.
    • 
      
  • Place feature-scoped services directly in the feature module or use providedIn: 'root' for singletons.
    • 
      
  • Prefer lazy loading for any route the user may never visit in a session.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Creating circular imports — Module A imports Module B and vice versa. Extract shared pieces to SharedModule.
    • 
      
  • Importing FormsModule in AppModule and expecting it in lazy-loaded feature modules — it won't work.
    • 
      
  • Using RouterModule.forRoot() in a feature module — creates a second router, breaking navigation.
    • 
      
  • Declaring a component in two modules — Angular throws a "declared in multiple modules" error.
    • 
      
  • Not grouping feature assets in a folder — leads to a flat, hard-to-navigate project structure.
    •
