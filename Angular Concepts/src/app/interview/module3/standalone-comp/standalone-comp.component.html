Standalone Components

Angular 14+ components that own their dependencies — no NgModule wrapper required

📌 Definition

A Standalone Component is an Angular component decorated with standalone: true inside @Component. It manages its own dependency imports (other components, directives, pipes, and modules) directly in its imports array, bypassing the NgModule declaration system entirely. Introduced in Angular 14 and made the default scaffolding target in Angular 17, standalone components simplify the architecture by co-locating a component with everything it needs.

🤔 Why is it needed?

  • Reduced boilerplate — no need to declare in a module, manage exports, or maintain a separate module file.
  • Better tree-shaking — bundlers can statically determine exactly what each component uses and eliminate the rest.
  • Simpler mental model — dependencies are listed where the component is defined, not in a separate module file.
  • Granular lazy loading — routes can use loadComponent to load a single file, not a whole module.
  • Easier testing — TestBed only needs the component and its direct imports, not an entire module tree.

🌐 Real-time Example

    

      A new Angular 17 app scaffolds with bootstrapApplication and standalone routes. The
      DashboardComponent and UserProfileComponent are each loaded on demand
      using loadComponent. Each imports only the components and directives it needs, resulting
      in smaller per-route bundles and faster initial page load.
    

    

  


  

    
⚙️ Internal Working

    

      In AOT compilation, Angular analyses each standalone component's imports array at build time.
      It creates a standalone component factory that contains a compiled template with direct references to
      imported dependencies — no NgModule factory is needed as an intermediary. When loadComponent
      triggers a dynamic import(), only the component file and its transitive standalone imports
      are bundled in that chunk. Angular's compiler performs dead-code elimination at the import graph level,
      removing unused directives and pipes from the bundle.
    

  


  

    

      
✅ Advantages

      
    
        
  • Eliminates NgModule boilerplate — fewer files, less cognitive overhead.
    • 
        
  • Optimal tree-shaking — unused imports are not bundled.
    • 
        
  • Supports loadComponent for single-component lazy loading.
    • 
        
  • Simpler unit tests — no module setup needed in TestBed.
    • 
        
  • Default in Angular 17+ — aligns with the framework's future direction.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Migration effort — large existing NgModule apps require incremental conversion.
    • 
        
  • Each component must import its own dependencies — can feel repetitive for large shared sets.
    • 
        
  • Some older libraries have not yet published standalone APIs.
    • 
        
  • Developers new to Angular may confuse component-level imports with module-level imports.
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use standalone: true for all new components in Angular 14+ projects.
    • 
      
  • Configure providers in app.config.ts using provideRouter, provideHttpClient, etc.
    • 
      
  • Use loadComponent in routes for per-page lazy loading without module wrappers.
    • 
      
  • Migrate existing apps incrementally — convert leaf components first, then move up the tree.
    • 
      
  • Run ng generate --standalone as the default schematic flag for new projects.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Adding a standalone component to an NgModule's declarations — use imports instead.
    • 
      
  • Forgetting to import CommonModule (or specific directives like NgIf, NgFor) — template errors at runtime.
    • 
      
  • Importing BrowserModule inside a standalone component — only needed in the root bootstrapper.
    • 
      
  • Using loadChildren for standalone components — use loadComponent instead.
    • 
      
  • Mixing bootstrapModule(AppModule) with standalone routing without migration steps — results in configuration conflicts.
    •
