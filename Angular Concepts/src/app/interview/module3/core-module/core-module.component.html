Module 3 — Modules

Core Module

Singleton services and app-wide infrastructure — import once in AppModule, never again

📌 Definition

CoreModule is an NgModule designed to hold singleton services, HTTP interceptors, route guards, and other app-wide providers that must exist as a single instance for the lifetime of the application. It is imported exactly once in AppModule. It includes a constructor guard (using @Optional() @SkipSelf()) that throws a descriptive error if any other module tries to import it, preventing accidental creation of duplicate service instances.

🤔 Why is it needed?

  • Single DI instance — AuthService, LoggingService, and interceptors must be singletons; CoreModule enforces this.
  • Keeps AppModule lean — centralising providers in CoreModule prevents AppModule from becoming a monolithic mess.
  • Interceptor registration — HTTP interceptors must be registered using HTTP_INTERCEPTORS multi-provider tokens; CoreModule is the right home.
  • Guards and resolvers — route guards protecting the whole app belong in CoreModule.
  • Error handling — global error handlers and loggers are registered once here.

🌐 Real-time Example

    

      In a banking application, CoreModule provides AuthService (login/logout/session),
      LoggingService (audit trail), and a TokenInterceptor that attaches the JWT to every
      HTTP request. Because CoreModule is imported only in AppModule, these services are guaranteed singletons —
      the same AuthService instance is used in every page, from the login screen to the dashboard.
    

    

  


  

    
⚙️ Internal Working

    

      Angular's dependency injection tree has a root injector created by AppModule. When
      CoreModule is imported in AppModule, its providers array is merged into the root
      injector. Any component or service in the app that injects AuthService receives the same
      instance because the root injector is a singleton store. The @Optional() @SkipSelf()
      constructor parameter works by asking the injector to look above the current module for an existing
      CoreModule token. If found, it means CoreModule was already imported, triggering the guard error.
    

  


  

    

      
✅ Advantages

      
    
        
  • Guarantees singleton services — one instance per token for the app lifetime.
    • 
        
  • Constructor guard provides a clear, developer-friendly error on misuse.
    • 
        
  • Centralises cross-cutting concerns (auth, logging, error handling) in one module.
    • 
        
  • Keeps AppModule and feature modules focused on their own responsibilities.
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Extra boilerplate — modern Angular prefers providedIn: 'root' on services instead.
    • 
        
  • HTTP interceptors and multi-provider tokens still require explicit registration in CoreModule.
    • 
        
  • Developers unfamiliar with the pattern may still try to import it in feature modules.
    • 
        
  • Less relevant in standalone Angular 17+ apps that use provideHttpClient(withInterceptors([...])).
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always import CoreModule only in AppModule — never in feature modules.
    • 
      
  • Include the @Optional() @SkipSelf() guard in every CoreModule constructor.
    • 
      
  • Use providedIn: 'root' for simple services; use CoreModule for HTTP interceptors and tokens.
    • 
      
  • Do not add UI components to CoreModule — those belong in SharedModule.
    • 
      
  • In standalone apps, replace CoreModule with app.config.ts using provideHttpClient, provideRouter, etc.
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Importing CoreModule in a feature module — creates duplicate service instances and breaks singletons.
    • 
      
  • Forgetting the constructor guard — allows silent duplicate imports without any error.
    • 
      
  • Putting UI components in CoreModule — they can't be easily shared and don't belong here.
    • 
      
  • Using CoreModule for services that are feature-scoped — those should live in their own feature module.
    • 
      
  • Not registering HTTP interceptors with multi: true — replaces rather than chains interceptors.
    •
