Angular Architecture

The 8 core building blocks — Modules, Components, Templates, Services, DI, Directives, Pipes, and Router.

📌 Definition

Angular's architecture is built on 8 core building blocks that work together to form a complete application. At the center is the Component — a self-contained unit of UI and logic. Components live inside NgModules (or standalone configurations), consume shared logic from Services via Dependency Injection, transform data with Pipes, extend HTML with Directives, and navigate between views via the Router. All of these are defined using TypeScript decorators (metadata annotations).

🤔 Why is it needed?

  • Component model: Breaks complex UIs into reusable, testable, isolated pieces.
  • DI system: Manages object creation and lifetime, enabling loose coupling and easy testing.
  • Module system: Groups related features into cohesive units with clear public APIs.
  • Template system: Declarative HTML-based views with Angular-specific syntax for data binding and directives.
  • Services: Centralize shared business logic and state, keeping components lean.
  • Router: Provides declarative, URL-driven navigation without page reloads.

🌐 Real-time Example

    
A login feature demonstrates all 8 building blocks working together: the Router maps /login to LoginComponent; the Component handles the view logic; its Template uses [(ngModel)] (two-way binding) and (click) (event binding); a Directive adds input highlighting; a Pipe formats validation messages; AuthService (a Service) handles the HTTP call; the DI system injects AuthService; and the feature lives inside AuthModule.

    

  


  

    
⚙️ Internal Working

    
Angular's runtime builds an injector tree that mirrors the module/component hierarchy. The root injector holds app-wide singletons (services with providedIn: 'root'). Each module and component has its own injector for scoped services. When a component is rendered, Angular processes its template — resolving property bindings, registering event listeners, and instantiating child components. Change detection (triggered by Zone.js or Signals) traverses the component tree, comparing current and previous values and patching only changed DOM nodes. Components are destroyed when navigating away, triggering ngOnDestroy for cleanup.

  


  

    

      
✅ Advantages

      
    
        
  • Clear separation of concerns — component, service, template each have distinct roles
    • 
        
  • Hierarchical DI makes services testable with mock implementations
    • 
        
  • Reusable components, directives, and pipes across modules
    • 
        
  • Declarative templates are readable and close to HTML
    • 
        
  • Module boundaries enforce encapsulation in large codebases
    • 
        
  • Standard architecture means any Angular developer can navigate any Angular project
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Learning all 8 building blocks simultaneously is challenging for beginners
    • 
        
  • NgModule boilerplate (declarations, imports, exports) adds verbosity
    • 
        
  • Over-engineering risk — creating modules and services for trivial features
    • 
        
  • Circular dependency issues when services inject each other
    • 
        
  • Choosing between NgModule vs standalone architecture requires a decision
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Follow the Single Responsibility Principle — one component per file, one purpose per service
    • 
      
  • Use providedIn: 'root' for app-wide singleton services
    • 
      
  • Place shared components/pipes/directives in a SharedModule or shared/ folder
    • 
      
  • Place singleton services in CoreModule (or core/ with providedIn: 'root')
    • 
      
  • Use Smart/Dumb component pattern — smart (container) components fetch data; dumb (presentational) components display it
    • 
      
  • Prefer standalone components over NgModule for new Angular 15+ projects
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Importing BrowserModule in feature modules — only import it in AppModule
    • 
      
  • Creating God services with too many responsibilities
    • 
      
  • Putting HTTP calls directly in components instead of services
    • 
      
  • Forgetting to declare or import components (they just don't render, no clear error)
    • 
      
  • Creating circular service dependencies — A injects B, B injects A
    • 
      
  • Not exporting components from their module — they are invisible to other modules
    •
