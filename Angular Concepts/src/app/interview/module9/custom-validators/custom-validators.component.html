Module 9 — Forms

Custom Validators

Write your own validation logic — synchronous, async, and cross-field

📌 Definition

Custom validators are functions (or directives for template-driven forms) that encapsulate application-specific validation logic. They accept an AbstractControl and return ValidationErrors | null synchronously, or Observable<ValidationErrors | null> asynchronously. They integrate with Angular's form status system exactly like built-in validators.

🤔 Why is it needed?

  • Built-in validators only cover basic cases — real apps need password confirmation, business rule checks, and dependent field validation
  • Async validators enable server-side checks such as username uniqueness or email domain verification
  • Cross-field validators compare two controls (e.g., date range start before end) — only possible at the FormGroup level
  • Reusable — custom validators are plain functions that can be shared and unit-tested independently

🌐 Real-time Example

    
A registration form uses two custom validators: a synchronous cross-field passwordMatch validator applied at the FormGroup level, and an async usernameAvailable validator that calls the backend API with debouncing via a factory function pattern to avoid DI issues.

    

  


  

    
⚙️ Internal Working

    
Angular calls custom validators through the same pipeline as built-in ones. For sync validators, the return value is merged into control.errors immediately. For async validators, Angular sets status to PENDING, subscribes to the returned Observable (or awaits the Promise), and once it completes, merges the result into control.errors and emits a statusChanges event. For FormGroup-level validators the same logic applies, but errors land on the FormGroup's errors property instead of a child control's.

  


  

    

      
✅ Advantages

      
    
        
  • Unlimited flexibility — encapsulate any business rule as a reusable, independently unit-testable function
    • 
        
  • Cross-field validation is clean — apply one validator at the FormGroup level rather than duplicating logic in both controls
    • 
        
  • Async validators let you defer to the server for uniqueness or domain-specific checks with a native PENDING state
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Async validators require careful debouncing and Observable completion (first/take(1)) to avoid hanging PENDING state
    • 
        
  • Template-driven usage requires creating a directive with NG_VALIDATORS — more boilerplate than the reactive equivalent
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use a factory function pattern for async validators that depend on services to keep them pure and injectable-friendly
    • 
      
  • Always call first() or take(1) in async validators to ensure the Observable completes and Angular resolves the status
    • 
      
  • Apply cross-field validators at the FormGroup level and guard with null checks on control.parent during initialisation
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Applying a cross-field validator on a child FormControl — use control.parent, but the error lands on the wrong level; apply at the FormGroup instead
    • 
      
  • Forgetting first() in an async validator — the Observable never completes, the control stays PENDING indefinitely
    •
