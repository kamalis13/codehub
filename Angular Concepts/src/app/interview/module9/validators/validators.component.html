Module 9 — Forms

Validators

Built-in form validation — enforce data integrity with zero boilerplate

📌 Definition

The Validators class provides a set of static factory functions that return synchronous validator functions. Each validator checks a FormControl's value and returns null when valid, or a ValidationErrors object with descriptive error keys when invalid. Validators are composable — multiple validators can be combined by passing them as an array.

🤔 Why is it needed?

  • Enforces data integrity without writing custom logic for common rules (required, email, length, range)
  • Provides consistent, well-tested validation behaviour across all reactive forms in the application
  • Composable — combine multiple validators on a single control and Angular runs them all, collecting error keys
  • Integrates cleanly with template error display via control.errors and Angular's form status system

🌐 Real-time Example

    
A user registration form applies multiple built-in validators to each field: the username must be required and between 3 and 20 characters, the email must be valid, age must be between 18 and 120, and the website URL must match an https pattern. Each error type is displayed separately in the template.

    

  


  

    
⚙️ Internal Working

    
Each built-in validator is a factory function that returns a ValidatorFn: (control: AbstractControl) => ValidationErrors | null. Angular's FormControl calls composed validators on every value change. If a validator returns a non-null object, its keys are merged into control.errors. The control's status transitions to INVALID and statusChanges emits. All sync validators run before any async validators are triggered.

  


  

    

      
✅ Advantages

      
    
        
  • No boilerplate — covers the most common validation rules with a single import
    • 
        
  • Easily composable — pass an array of validators and Angular applies them all, collecting each error key
    • 
        
  • Well-tested by the Angular team — no risk of edge cases in standard rules like email format checking
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Limited to common cases — business-specific rules (password match, username uniqueness) require custom validators
    • 
        
  • Validators.email uses a simple regex that may accept technically valid but unusual formats
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Always show validation errors only when the control is touched or the form is submitted to avoid alarming pristine users
    • 
      
  • Prefer Validators.pattern with a well-documented regex and add a comment explaining what it matches
    • 
      
  • Use Validators.compose() explicitly when building reusable validator sets that need to be shared across components
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Relying on the HTML required or minlength attribute instead of Validators — Angular's control.errors will not reflect it
    • 
      
  • Checking control.errors.required instead of control.errors?.['required'] — the former throws if errors is null
    •
