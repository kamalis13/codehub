Session Storage

Per-tab, per-session key-value storage — automatically cleared when the tab closes, ideal for wizard/form state

📌 Definition

sessionStorage is a Web Storage API that provides key-value storage scoped to a single browser tab session. Data persists as long as the tab is open (surviving page reloads and Angular route changes within the tab) but is automatically deleted when the tab or browser window is closed. Unlike localStorage, sessionStorage is isolated per tab — two tabs from the same origin have completely separate, independent sessionStorage instances.

🤔 Why is it needed?

  • Auto-cleanup on tab close — no manual eviction needed for temporary session data
  • Tab isolation — different tabs can have different view states for the same app
  • Multi-step wizard state — data persists across route navigation but not across sessions
  • Temporary OAuth state (PKCE verifier, nonce) that should not persist
  • Security — sensitive temp data is automatically discarded when the tab closes

🌐 Real-time Example

    
A multi-step registration wizard saves form data at each step to sessionStorage. If the user navigates back (browser back button or Angular Router navigation), the previous step's data is pre-populated from sessionStorage. When the form is submitted, sessionStorage is cleared. If the user abandons the form and closes the tab, the data is automatically discarded — no stale registration data in storage.

    

  


  

    
⚙️ Internal Working

    
sessionStorage is maintained by the browser per browsing context (tab). Each tab gets its own isolated storage bucket, even for the same origin. The browser automatically clears it when the browsing context (tab or window) is destroyed. In Angular SPAs, route changes do NOT clear sessionStorage because Angular Router navigates without destroying the browsing context. sessionStorage uses the same underlying storage mechanism as localStorage (typically SQLite or browser-native storage) but with different lifetime and isolation semantics.

  


  

    

      
✅ Advantages

      
    
        
  • Automatic cleanup on tab close — no manual eviction logic needed
    • 
        
  • Tab-isolated — different tabs can maintain independent application states
    • 
        
  • Survives page reloads and Angular route changes within the same tab
    • 
        
  • Same simple API as localStorage — easy to use
    • 
        
  • No expiry dates to manage — session-based lifetime is implicit
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Data lost when tab closes — not suitable for persistent preferences
    • 
        
  • Not shared across tabs — cannot synchronize state between windows
    • 
        
  • XSS-vulnerable — JavaScript on the same origin can read it
    • 
        
  • Not available in SSR (Node.js) — requires platform guards
    • 
        
  • ~5MB limit — same as localStorage, insufficient for large datasets
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Use for transient state that should auto-expire: wizards, multi-step forms, temporary filters
    • 
      
  • Namespace keys with a prefix to avoid collisions: reg_step1, checkout_cart
    • 
      
  • Wrap in an Angular service with try-catch for QuotaExceededError and JSON errors
    • 
      
  • Guard with isPlatformBrowser(platformId) for Angular Universal compatibility
    • 
      
  • Explicitly call sessionStorage.removeItem() on form submission for immediate cleanup
    • 
      
  • Never store sensitive credentials — sessionStorage is still JS-accessible (XSS risk)
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Using sessionStorage for data that should persist across sessions (use localStorage)
    • 
      
  • Expecting sessionStorage to be shared across tabs — each tab is isolated
    • 
      
  • Not using JSON.parse/stringify for object storage
    • 
      
  • Accessing sessionStorage in Angular Universal without SSR guard
    • 
      
  • Storing sensitive data (tokens, passwords) in sessionStorage — XSS can read it
    •
