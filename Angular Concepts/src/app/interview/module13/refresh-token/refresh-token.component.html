Module 13 — Authentication

Refresh Token

Long-lived credential enabling silent access token renewal — keeping users logged in without re-authentication

📌 Definition

A refresh token is a long-lived credential (typically 7–30 days) issued by the authentication server alongside the short-lived access token. Its sole purpose is to obtain new access tokens without requiring the user to log in again. When the access token expires (after 5–15 minutes), the client silently exchanges the refresh token for a fresh access token — creating a seamless experience. Refresh tokens are stored server-side and can be revoked, unlike stateless JWTs.

🤔 Why is it needed?

  • Short access token expiry limits breach window; refresh token enables session continuity
  • Provides server-side revocation — can invalidate a refresh token on logout or breach detection
  • Enables "remember me" functionality across browser sessions
  • Token rotation detects stolen refresh tokens by invalidating used tokens
  • Smooth UX — users never see a login prompt when their access token silently expires

🌐 Real-time Example

    
An Angular interceptor handles the full refresh flow. When a 401 is received, it checks a isRefreshing flag to prevent duplicate refresh calls. A BehaviorSubject queues concurrent 401 requests until the refresh completes, then retries all of them with the new token. If the refresh itself fails, the user is logged out.

    

  


  

    
⚙️ Internal Working

    
At login, the server issues two tokens: a short-lived access JWT (in response body or memory) and a long-lived refresh token (in an httpOnly cookie). The access token is sent in every API request's Authorization header. When the server returns 401 (token expired), the Angular interceptor calls POST /auth/refresh. The browser automatically sends the httpOnly refresh token cookie. The server validates it, issues a new access JWT, and optionally a new refresh token (rotation). The interceptor updates the in-memory access token and retries the original request.

  


  

    

      
✅ Advantages

      
    
        
  • Short access token expiry limits damage from token theft
    • 
        
  • Server-side revocation enables immediate logout across all sessions
    • 
        
  • httpOnly cookie storage makes refresh token inaccessible to JavaScript (XSS-safe)
    • 
        
  • Token rotation enables theft detection
    • 
        
  • Transparent to users — no repeated login prompts during normal usage
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • Complexity — refresh logic, queueing, and rotation add significant interceptor code
    • 
        
  • Refresh token must be stored server-side for revocation (adds state to otherwise stateless auth)
    • 
        
  • Race condition risk — multiple simultaneous 401s need careful queueing
    • 
        
  • Refresh token theft (e.g., from cookie) is still a risk if SameSite is not configured
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Store refresh tokens in httpOnly, Secure, SameSite=Strict cookies — never localStorage
    • 
      
  • Implement token rotation — issue a new refresh token on every refresh request
    • 
      
  • Use a BehaviorSubject queue in the interceptor to handle concurrent 401s
    • 
      
  • Force logout (clear token, navigate to /login) when refresh itself returns 401/403
    • 
      
  • Set refresh token expiry based on business need — shorter for sensitive apps, longer for consumer apps
    • 
      
  • Store refresh tokens in a DB with user association — enables server-side revocation on logout
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Storing refresh tokens in localStorage — XSS can steal them, enabling permanent account access
    • 
      
  • Not handling concurrent 401s — multiple parallel refresh calls invalidate each other
    • 
      
  • Not implementing token rotation — stolen refresh tokens are reusable indefinitely
    • 
      
  • Infinite retry loop — not catching the case where the refresh endpoint itself returns 401
    • 
      
  • Setting access token expiry too long (hours/days) — defeats the security purpose
    •
