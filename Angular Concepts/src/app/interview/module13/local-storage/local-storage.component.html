Local Storage

Browser persistent key-value storage — data survives browser restarts, scoped to origin, ~5MB limit

📌 Definition

localStorage is a Web Storage API built into browsers that provides a synchronous key-value store persisting data indefinitely — until the user or application explicitly clears it. Unlike cookies, localStorage is not sent with HTTP requests. It is scoped to the origin (scheme + hostname + port) and accessible to any JavaScript on that origin. Each key-value pair must be a string — objects are stored using JSON.stringify and retrieved with JSON.parse.

🤔 Why is it needed?

  • Persists user preferences (theme, language, layout) across sessions
  • Caches API responses to reduce load time on returning visits
  • Stores non-sensitive tokens or feature flags that must survive page refresh
  • Cross-tab data sharing via the storage event for same-origin tabs
  • Simpler API than cookies — no expiry, path, or domain headers to manage

🌐 Real-time Example

    
A StorageService wraps localStorage with TypeScript generics, error handling (QuotaExceededError, malformed JSON), and SSR guards. A ThemeService uses it to persist the user's dark/light mode preference, initialized from localStorage on startup and updated via a BehaviorSubject that the app reacts to reactively.

    

  


  

    
⚙️ Internal Working

    
localStorage is implemented by the browser as a persistent database (SQLite in Chrome, for example) on disk. Reads and writes are synchronous — the browser blocks the JavaScript thread until the operation completes. Data is scoped by origin: the browser enforces strict origin isolation. The storage event is dispatched to all other browsing contexts (tabs/windows) from the same origin when the storage changes, but NOT to the originating tab. The storage API is defined in the HTML Living Standard (WHATWG) and is available in all modern browsers.

  


  

    

      
✅ Advantages

      
    
        
  • Simple, synchronous API — easy to read and write without callbacks
    • 
        
  • Persistent across browser restarts — ideal for user preferences
    • 
        
  • ~5MB storage per origin — sufficient for most configuration and small cache needs
    • 
        
  • Cross-tab synchronization via the window storage event
    • 
        
  • No expiry to manage — data stays until explicitly removed
    • 
      

    

    

      
❌ Disadvantages

      
    
        
  • XSS-vulnerable — any JS on the origin can read it (never store JWT/sensitive tokens here)
    • 
        
  • Synchronous — blocks main thread (performance issue for large/frequent operations)
    • 
        
  • Strings only — all values must be serialized/deserialized
    • 
        
  • Not accessible in Service Workers or Web Workers
    • 
        
  • Not available in SSR (Node.js) — requires platform guards in Angular Universal
    • 
      

    

  


  

    
🏆 Best Practices

    
    
      
  • Wrap in an injectable Angular service with error handling (QuotaExceededError, JSON parse errors)
    • 
      
  • Use TypeScript generics in the service wrapper for type safety
    • 
      
  • Guard with isPlatformBrowser(platformId) for SSR compatibility
    • 
      
  • Cache frequently-read values in memory (BehaviorSubject) to avoid repeated synchronous reads
    • 
      
  • Never store JWTs or sensitive tokens in localStorage — use httpOnly cookies
    • 
      
  • Namespace keys (e.g., app_theme, app_user_prefs) to avoid collisions with third-party scripts
    • 
    

  


  

    
⚠️ Common Mistakes

    
    
      
  • Storing JWTs or sensitive data — XSS can steal them
    • 
      
  • Not wrapping setItem in try-catch — throws QuotaExceededError when storage is full
    • 
      
  • Forgetting JSON.parse/stringify — returns "[object Object]" when storing objects directly
    • 
      
  • Accessing localStorage in Angular Universal without an SSR guard
    • 
      
  • Not cleaning up the storage event listener in ngOnDestroy
    •
